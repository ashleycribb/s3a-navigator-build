## 1. Overview

`s3a-kite` is an S3A **add-on pack** that forks Kitesurf's Apache-2.0 Rust core (vendored from [ashleycribb/s3a-Kite](https://github.com/ashleycribb/s3a-Kite) at the pin above) and replaces Kitesurf's Cloudflare TypeScript host with a native host and a UniFFI library inside the S3A mobile app.

s3a-kite **is** the S3A viewer. It reads `.s3a` and Edge files with `s3a-engine` / `s3a-edge` and paints the manifest or header sheet and the warehouse tour with Kitesurf's Rust layout and CPU rasterizer. Wiki Markdown and local HTML are painted by `render_page`. On a hub or PC with a display, an optional **native window** is a Host HTTP API client: it sends the UI token on every request except the tokenless health case (DD-60). The Host HTTP API in §5.2.1 is the only write path and the testable wire contract. It is not a Chrome DevTools server. Headless hosts (Aura Rack, LRS VM, or a lab PC without a display) run with `--headless` and no window. The phone app, in v1, is an S3A / Edge-tile viewer only (DD-45, DD-128). It has no Scholar 3-pass / literature-review flow: no candidate list, select, download, inclusion, snapshots, consent, LRS, or `paper_identity`. There is no phone Scholar Explorer. AI Teacher's Assistant chat and phone paper search are future, unbuilt, and out of scope for this spec (DD-128, Q-15, Q-16); this spec adds no ATs, exports, or interfaces for either.

First product use, on the hub or PC: Scholar's wiki browser for Keshav's 3-pass method. Pass 1 is a human skim of about 15 seconds and is never recorded. Selecting or downloading a paper is the inclusion decision and is written to the researcher's working archive even when tracing consent is off. Tracing is consent-only xAPI to `s3a-lrs-server`. AI and the browser only check that things exist and record what the researcher did; humans make the judgments. Custody of the UI token file is the human-control point for every write, including those issued by the native window (DD-32, DD-60).

S3A core stays database-only. No money and no cryptocurrency. Everything lives in the pack.

A v1 **Scholar-mode** host process serves **one researcher**, requires **durable local disk**, and runs on an Aura Rack, the LRS VM, or a lab PC (DD-48, DD-78). Viewer-only mode does not require a data directory. Cloud Run is not a v1 target. The host process itself is specified for Unix (Linux) only in v1 (DD-73).

### 4.1 Kitesurf

*   Experimental browser engine that parses HTML, applies CSS, runs page JavaScript, and renders screenshots without Chrome (`README.md`). Licensed Apache-2.0 (`LICENSE`); bundled fonts and crates keep their licenses (`NOTICE`).
*   Cloudflare deployment requires Dynamic Workers (Workers Paid) and `wrangler dev` locally (`README.md` "IMPORTANT" block). `packages/engine/wrangler.jsonc` declares `"worker_loaders": [{ "binding": "LOADER" }]`. Page isolates are started with `env.LOADER.load({...})` in `packages/engine/src/eval/page-script.ts` at line 368 in `235111c` (line 376 in `4a29038`).
*   Commit `235111c` (`engine: slim what each page isolate receives at startup`) changes only TypeScript. Each PageScript and renderer isolate previously received the 27 MB core Wasm as bytes and recompiled it on every navigation. The parent now passes its already compiled `WebAssembly.Module`, and the generated startup-input module embeds `hasHtml` and `htmlLength` instead of the navigated HTML string. Files: `packages/engine/src/eval/page-renderer.ts`, `page-script.ts`, two engine tests, `packages/page-script/src/__ks_startup_probe_input.ts`, and `startup-probe.ts`. This does not change the Rust core and does not provide a native-host page-JS runtime.
*   The engine has no authentication of its own. A person who has the URL can open DevTools, connect Puppeteer, and send outbound requests (`README.md`, Cloudflare deployment warning).
*   Stack, from `README.md` "Technology stack": Blitz (HTML/DOM/layout/paint, MIT OR Apache-2.0); Stylo (CSS, **MPL-2.0**); Boa (page JavaScript inside WebAssembly, Unlicense OR MIT); Linebender libraries (Parley, Vello, Kurbo, Peniko, Apache-2.0 OR MIT); Krilla (PDF output, MIT OR Apache-2.0).
*   `packages/core/Cargo.toml` describes `kitesurf-core` as "Wasm core for kitesurf: DOM data plane + Stylo + Blitz render." `crate-type` is `["cdylib", "rlib"]`. Feature `native-host` is declared and is used to drop `wasm_bindgen` exports (for example `packages/core/src/paint/scene_replay.rs`, `tty/grid.rs`).
*   Page JavaScript evaluation lives in `packages/core/src/js.rs` and `packages/core/src/js/boa_eval.rs`, both gated `#[cfg(target_arch = "wasm32")]`. There is no native-host Boa entry point in the tree today. `packages/core/Cargo.toml` notes that Boa pulls `getrandom` 0.2, which on `wasm32-unknown-unknown` needs the `js` feature.
*   **Paint backend is CPU, not GPU.** Workspace pins `vello_cpu` 0.3 with features `std`, `text`, `u8_pipeline`, `poly-pnorm`, and `anyrender_vello_cpu` 0.18, both `default-features = false` (`Cargo.toml`). Screenshots use `anyrender_vello_cpu::VelloCpuImageRenderer` (`packages/core/src/paint/screenshot.rs`, `scene_replay.rs`). There is no `wgpu`, Vulkan, Metal, or GLES dependency in those manifests. Raster output is a CPU `vello_cpu::Pixmap` / RGBA buffer, then PNG or JPEG.
*   **Fonts are bundled, not system fonts.** `make_empty_font_context` sets `CollectionOptions { shared: true, system_fonts: false }` (`packages/core/src/resources/fonts.rs`). UA fonts live under `packages/engine/public/fonts/` (the directory is about 19 MB, 55 files, SIL OFL 1.1 per `NOTICE`). Production registration is `register_ua_fonts` from host-supplied bytes; tests `include_bytes!` Noto Sans, Italic, Serif, Mono, and Symbols. Noto Color Emoji (about 1.9 MB) and Noto Sans SC (about 5.9 MB) exist as separate assets. Blitz's `system_fonts` feature is deliberately off in `packages/core/Cargo.toml`.
*   `kitesurf-cli` is a terminal client. It downloads a Wasm scene rasterizer and runs it in **Wasmtime** 36 (`packages/kitesurf-cli/Cargo.toml`, `packages/kitesurf-cli/src/wasm.rs` "Calls the scene-host Wasm ABI through Wasmtime"). That is a client playback path, not the Cloudflare host, and it is not a page-JS runtime.
*   Boa is used to run page `Runtime.evaluate` expressions in the core Wasm (`packages/core/Cargo.toml`). Page `WebAssembly.*` is shimmed in `packages/page-script/src/globals.ts`. **s3a-kite does not use Boa or that shim to run an old S3A viewer.** Opening a `.s3a` file does not instantiate the page JavaScript runtime. **Boa is not used in v1** (DD-26 as amended, DD-44): there is no page JS, no Wasmtime, and no Boa isolate on the host or phone.
*   Upstream CDP lives in TypeScript under `packages/engine/src/cdp/` (modules include `page.ts`, `runtime.ts`, `dom.ts`, `network.ts`, `input.ts`, `target.ts`, `debugger.ts`, `accessibility.ts`, `fetch.ts`, and others).

### 4.2 S3A tour and manifest

*   `s3a-cli tour [--json] [--floor N] [--slice] [--cross] [--history] <archive>` and `s3a-cli tour --html <archive> <out.html>` are implemented in `crates/s3a-cli/src/tour.rs`, `tour_html.rs`, and `tour_html_template.html`.
*   `tour_file` builds a `TourReport` with a `TourLobby`. If a floor has `type_id == TileType::MANIFEST` (`s3a-core`: `MANIFEST = 78`), the UTF-8 payload is `lobby.manifest`. Plain-text output prints `--- PLAIN-TEXT MANIFEST ---` then that payload (`print_tour_report`). The test `test_tour_displays_manifest_in_lobby_and_floor` expects `THIS IS AN S3A FILE` and the seal title/creator.
*   Default mode lists the floor directory. `--floor N` is floor detail (schema fields, records, `withheld_count`). Consent, as described in the `tour.rs` header comment: when consent records exist, records without active `purpose=research` are withheld. Separately, `evaluate_consent_summary` returns `"open / unrestricted (no consent records)"` when there are no consent records, no withdrawal marks, and no Edge consent value. Kite follows that no-records-unrestricted rule for both Edge files (no type 71) and hyper-tile files (no core `ConsentRecord`s). The **only normative withholding rule** for kite is §5.3 item 4 (hyper-tile) and §5.4 item 6 (Edge). This paragraph is a source fact about `tour.rs`, not a second algorithm. v1 has no unfiltered or staff view mode.
*   `tour --html` embeds the same JSON, escaped so archive text cannot break out of a `<script type="application/json">` block, and renders with `textContent`, never `innerHTML` (`tour_html.rs`).
*   The HTML animation: clicking a tile opens `#card`. The card is first placed on the tile's bounding rect at opacity 0.2 with `transition: none`, then on a double `requestAnimationFrame` the transition is restored (unless the hash has `instant`) and the card moves to `left: 6vw; top: 8vh; width: 88vw; height: 84vh; opacity: 1`. CSS: `#card { transition: all .45s cubic-bezier(.2,.8,.2,1); }` (`tour_html_template.html`).
*   The unsealed fallback in `tour.rs` walks tiles at `FILE_HEADER_SIZE + i * HYPER_TILE_SIZE` (512 + *i* × 128 KiB). It does **not** consult `tile_stride`. Edge 4 KiB / 8 KiB archives are therefore not toured correctly by today's CLI scanner. s3a-kite must use `s3a_engine::MmapReader` (`is_edge_archive()`, `tile_stride()`, `header_extent()`, edge tile getters) instead of copying that loop.
*   `tour.rs` function `build_consent_state` contains a real branch `else if f.type_id == 82` that parses the payload as `EdgeConsentRecord` and may set `edge_research_allowed`. That is not only a comment. In `s3a-core`, 82 is `VCS_RESOLUTION`. Edge consent is `TILE_TYPE_CONSENT = 71` (`s3a-edge/src/header.rs`), with a different record layout than core consent. `s3a-engine/src/display_layouts.rs` warns that hyper-tile and edge archives reuse type numbers (64, 71, 75) and must be selected with `MmapReader::is_edge_archive`. s3a-kite must not copy the type-82 mistake. On a hyper-tile file that contains a type-82 tile, CLI `withheld_count` can be wrong; it is not a safe oracle for AT-11. Floor-list fields used by AT-10 (`index`, `type_id`, `record_count`, `size_bytes`, `payload_hash_short`) are not produced by that branch.
*   Timestamps in the tour and in sealed manifests are formatted with `humantime::format_rfc3339_seconds` from Unix epoch seconds (`tour.rs` `format_unix_timestamp`; a zero value prints `genesis`). That is UTC (`…Z`), not America/New_York. Kite uses the same function and timezone for header sheets, events, and snapshot capture time.
*   `FileHeader.version` is a `u16`. The writer sets it to 1. `FileHeader::verify` returns `S3AError::UnsupportedVersion` when it is not 1 (`s3a-core`: display text `Unsupported file version: {n}`). Magic that is not `S3A1` is `InvalidMagic` (`Invalid S3A file magic`). On mobile, `s3a-reader-core` surfaces a non-S3A file as `This is not an S3A file`.

### 4.3 Edge profile

From `docs/spec/S3A-EDGE-PROFILE.md` (cited as **EDGE §…** in this document) and `crates/s3a-edge`:

*   Phase 1 writer is `#![no_std]`, heapless, for MCUs with ≤ 32 KiB SRAM. Micro-tiles are exactly 4,096 or 8,192 bytes. Dual-slot header Variant A is 512 bytes; tile *i* is at `512 + i * tile_stride`. Variant B (`FLAG_COMPACT_HEADER`) uses extent `P = max(256, tile_stride)`. Because Edge strides are only 4096 or 8192, *P* is 4096 or 8192, never 256 or 512.
*   Flags: `FLAG_PROFILE_EDGE`, `FLAG_TILE_SIZE_4KB`, `FLAG_TILE_SIZE_8KB`, `FLAG_COMPACT_HEADER`, `FLAG_SEAL_CHAIN_ACTIVE`, `FLAG_ED25519_SIGNED`. Detection: `FLAG_PROFILE_EDGE` **or** `tile_stride` 4096 or 8192. Torn or unsealed micro-tiles are ignored, never treated as committed history.
*   Equipment event log is type 64, `EquipmentEventRecord` (32 bytes) with `event_type` 0x0001–0x0007 and `severity` 0=Info, 1=Warn, 2=Alarm, 3=Emergency (EDGE §5.2). Type 64 may also hold a 96-byte `DeviceIdentityRecord` (distinguish by `payload_len / record_count`). Every Edge archive MUST contain at least one `DeviceIdentityRecord` (EDGE §6.3) — that is a writer requirement.
*   Canonical `event_type` names (EDGE §5.2.2): `0x0001` `EVENT_MACHINE_START`, `0x0002` `EVENT_MACHINE_STOP`, `0x0003` `EVENT_EMERGENCY_STOP`, `0x0004` `EVENT_FAULT_CODE`, `0x0005` `EVENT_MAINTENANCE`, `0x0006` `EVENT_CALIBRATION`, `0x0007` `EVENT_OPERATOR_CHANGE`.
*   On-device trust is a SHA-256 seal chain (`S3AEDGE1` domain separation) and optional Ed25519 signatures in type 70. There is **no** tile 78 manifest in the Edge tile list (EDGE §12.2). A chain break is `S3AError::SealedChainBreak`: any modified, inserted, or reordered tile breaks the chain immediately (EDGE §6.1).
*   Conformance vectors `MICRO-VEC-01` (`micro_valid_4kb`), `MICRO-VEC-02` (torn tile), `MICRO-VEC-03` (signed seal chain) are generated in `crates/s3a-spec-vectors`.
*   EDGE §10 Phone Reader (Android first): verify CRC32C, payload hash, seal chain, Ed25519; store raw `.s3a`; show an event timeline (faults in red, maintenance in yellow, normal operations in green); optional later LRS sync and in-app consent writes. Phase 2 transports are not implemented. DD-07 colors by *severity* instead of that category coloring; §5.4 states the override and adds a non-color category cue.
*   Primary invariant (EDGE §1.2): every Edge file remains a valid S3A file readable by `s3a-engine` without transcoding.

### 4.4 3-pass, LRS, and writes

From `/workspace/3Pass/README.md` (repo [ashleycribb/3Pass](https://github.com/ashleycribb/3Pass)):

*   Pass 1 is the researcher's own skim. The AI only checks whether a record exists.
*   A paper gets a researcher record only when the researcher selects it for Pass 2/3.
*   `triage_wave.py` lists candidates; it does not score, rank, include/exclude, or record anything. Skipped papers are never recorded. The heading is "Pass 1: Your Skim (~15 s per paper)".
*   AI-extracted text is an AI draft and needs researcher judgment.

`s3a-pack-scholar` already defines the Scholar xAPI profile and tiles 10–15 (`HumanLrsRecord` is tile 10, 64 bytes, including `actor_hash`, `verb_id`, `timestamp_sec`, `object_hash`). `s3a-lrs-server` is the LRS (`POST /xapi/s3a/batch`). A unit test documents the client contract: consent off emits zero requests (`crates/s3a-lrs-server/src/main.rs`, `test_batch_sync_consent_off_client_contract`). The s3a-lrs VM is part of Ashley's lab and is outside the storage repo (`docs/design/research-lab-scenario.md`). Verb IRIs used for inclusion must come from `s3a-pack-scholar` `xapi.rs`; this spec does not invent a new IRI (Q-07).

Write APIs already in `s3a-engine`: `TileWriter::create`, `TileWriter::open_append`, `write_hyper_tile` / `write_hyper_tile_ext` / `write_raw_hyper_tile`, `enable_addon`, `try_lock_exclusive`, and `seal_archive` / `seal_archive_with_manifest` / `verify_sealed_archive` / `verify_sealed_bytes`. Opening a sealed archive with `open_append` does not modify it; the first append unseals it by dropping the seal trailer (`unseal_on_write` in `TileWriter`). Durability docs describe S3A as single-writer (`docs/durability.md`). Tiles 10–15 require `ADDON_EDU` (`0x0001`) per `docs/pack-contract.md`. Core `TileType::BLOB` is 68 and `TileType::PROVENANCE` is 72. Scholar pack `create_human_lrs` writes `HumanLrsRecord`s.

### 4.6 Pack contract

`docs/pack-contract.md`: browser and WebAssembly integrations stay out of `s3a-core` and `s3a-engine`. Addon bits already allocated: EDU, FINTECH (reserved), ROBOTICS, WEARABLE, GIS, DA, ONTOLOGY. Future packs that need new tile IDs start at 64+ with a new bit; the Clean pack uses existing core tiles and needs no new bit. v1 kite follows the Clean-pack pattern (DD-15, DD-16).

### 4.7 Facts used in v3, v4, and v5 dispositions

*   `s3a-pack-clean` `archive::chunk_tiles` / `unchunk` prefix each BLOB or PROVENANCE tile payload with a 32-byte key, a little-endian `u32` chunk index, and a little-endian `u32` total, then the chunk bytes (`crates/s3a-pack-clean/src/archive.rs`). The core registry describes the same 40-byte field layout for tiles 68 and 72 (`docs/spec/registry.md`). Hyper-tile payload size is `HYPER_TILE_SIZE - HYPER_TILE_HEADER_SIZE` (131,072 − 512).
*   `AcademicPaperRecord.paper_id` is a `u64` described as a hash of DOI / URI. The record has no URL or DOI string field (only `doi_prefix_hash`). `HumanLrsRecord` is 64 bytes: `session_uuid` ([u64; 2]), `timestamp_sec` (u64), `actor_hash` (**u64**), `verb_id` (u32), `decision_score` (f32), `ai_trace_coord`, `object_hash` (**u32**), `flags` (u32).
*   `s3a-pack-scholar` `xapi.rs` defines `hash_iri(&str) -> u64` as FNV-1a 64-bit with offset basis `0xcbf29ce484222325` and prime `0x100000001b3`. Scholar tests often use literal hashes; this function is the pack's existing string-to-`u64` hash. Verb IRIs and extensions `EXT_PAPER_ID`, `EXT_SOURCE_URL`, and `EXT_CONTENT_SHA256` live in the same file.
*   3Pass dossiers at `wiki/papers/SRC-XXXX.md` use YAML front matter whose keys in the grounded tree are `source_id`, `title`, `author`, `year`, `drive_path`, `provenance`, `wiki_category`, `theories` (and occasionally `PRACTICE`). None of the 287 dossiers in that tree has a `url` or `source_url` key. `drive_path` values are Windows Google Drive paths, not host-local paths.
*   `s3a-lrs-server` authenticates with HTTP Basic (`Authorization: Basic …`) from a credentials file of lines `user:password[:scopes[:archive]]`, or `--auth-user` / `--auth-pass`. It exposes `POST /xapi/statements` and requires `X-Experience-API-Version` of `1.0.x` (tests use `1.0.3`). `POST /xapi/s3a/batch` is a signed binary delta sync, not a JSON statement post.
*   Edge type-70 tiles hold one or more `DeviceSealRecord`s (144 bytes): `tile_index`, `generation`, `seal_hash`, `prev_seal_hash`, `signature` (Ed25519 over the 32-byte `seal_hash`), CRC. `MmapReader::edge_seal_records` returns each record with its `container_tile`. `edge_seal_chain` recomputes `compute_seal_hash` per tile in index order and stops at the first CRC-failed tile.
*   `tour.rs` `evaluate_consent_summary` returns status `"open / unrestricted (no consent records)"` when there are no consent records, no withdrawal marks, and no Edge consent value. That is the no-records behavior kite follows for Edge and hyper-tile files (DD-67).
*   `s3a-reader-core/src/verify.rs` defines `VerificationStatus` {`Unverified`, `Verified`, `SelfSigned`, `Unsigned`, `Quarantined`} and `SignerTrust` {`Embedded`, `Pinned`}. `verify(pinned_keys)` treats a non-empty pinned list as the trust anchor: a signer not in the list fails ("signer key not in pinned list"). An empty pin list yields at best `SelfSigned` (a signature against a `DeviceIdentityRecord` key is not independently trusted). s3a-vault `contacts.json` marks a contact `VERIFIED` only after `vault contact add` of the full 32-byte key; unpinned issuers are `UNKNOWN ISSUER`. S3A-EDGE-PROFILE.md §543 refers to a "cached or provisioned public_key."
*   `kitesurf-cli` downloads a Wasm scene rasterizer for playback; that download path is not used in v1 kite (DD-44). `boa_eval.rs` / `js.rs` remain wasm32-only; v1 does not invent a Wasmtime import ABI for them and does not depend on Boa or Wasmtime.

`Hit` is one of: `Continue`, `Floor(n)`, `Select { paper_id }`, `Link { href }`, `None`. `hit_test` is **pure**: it does not change handle state (DD-97).

*   `Continue` is only defined on `manifest`, `header`, or `banner` first views (the first-view aliases of `render_manifest`). After a `Continue` hit, the client must call `proceed_to_warehouse` / `POST /v1/proceed` to enter the warehouse. A Continue hit alone leaves the handle on the first view (AT-152).
*   `Floor(n)` is only defined on `warehouse`. `n` is the tile `index`. Invalid or omitted tiles are not hit-testable as `Floor(n)` (they may be listed in the banner text only).
*   `Select { paper_id }` is only defined on `view=page` when `select_enabled` was true for the last `render_page` and `paper_identity(handle)` is `Some`. The returned `paper_id` is that identity. A Select hit does **not** write an inclusion record; the host or native window must call `POST /v1/select` with the UI token (DD-58, DD-60). In viewer-only mode and on the phone, `select_enabled` is false and no Select control is painted (AT-144).
*   `Link { href }` is defined on `view=page` for a link box. The pack and the host do **not** fetch or open `href` automatically. A relative href is resolved against the **parent directory of the opened page**. A `#fragment` is stripped before resolution; a query string, if present, remains part of the path. If the resolved path canonicalizes inside an allowed request root, the UI may then call `POST /v1/open` with that path (AT-160). `http(s)` and `file://` hrefs are not opened or fetched from the page view in v1. The page view also loads **no subresources of any kind** (network or local) in v1 (DD-118, AT-121, AT-167).
*   `hit_test` on `floor-detail` or `floor-transition` (when a prior frame for that view **and floor** exists) returns `None`. Without a prior frame it is `409` `no_frame`. The last-frame cache is keyed by `(handle, view, floor)` (floor is 0 / unused for non-floor views).
*   A `hit_test` whose `view` is not valid for the handle's kind and state under §5.2.6 returns the same error as `/v1/frame` for that cell (`view_mismatch`, `not_archive`, or `unsupported`), checked **before** `no_frame` (AT-172).

v1 UniFFI on the phone exports `KiteContext::new`, `open`, `open_verified`, `close`, `proceed_to_warehouse`, the render functions, and `hit_test` (F-04, DD-128). It does not export `KiteContext::new_with_clock`, `open_path`, `paper_identity`, select, download, skip, consent, or write (DD-109). The app may run `s3a-reader-core` `verify(pinned_keys)` and pass the mapped `KiteVerificationReport` to `open_verified`, or call `open` and let the pack run the §5.4 algorithm. Pack `open` and a mapped reader-core `verify` of the same bytes and pin list must agree on `status`, `seal_status`, `invalid_tile_indices`, `break_index`, `torn_tile_indices`, and `quarantine_reason` (DD-115, AT-165). The pack does not depend on `s3a-reader-core`. `KiteVerificationReport` is a pack type with fields `status` (`verified` / `self_signed` / `unsigned` / `quarantined` / `unverified`), `seal_status` (`sealed` / `unsealed` / `seal_failed`), `tiles_crc_failed`, `invalid_tile_indices: Vec<u32>`, `break_index: Option<u32>`, `torn_tile_indices: Vec<u32>`, `quarantine_reason: Option<QuarantineReason>`, and `detail`. `QuarantineReason` is one of `crc`, `seal_trailer`, `chain_break`, `signature_known_signer`, `signer_not_pinned`, `missing_signature`. Pack `invalid_tile_indices` is every tile index that is **not** in the valid floor list. When no tile is a valid floor, it is every index in `0 .. tile_count-1`. The app maps a post-verify reader-core `VerificationReport` (s3a-reader `792742c`, `s3a-reader-core/src/verify.rs` and `integrity.rs`) by this table (DD-130):

| `KiteVerificationReport` field | Mapping from reader-core |
| --- | --- |
| `status` | `VerificationStatus`: `Unverified` → `unverified`, `Verified` → `verified`, `SelfSigned` → `self_signed`, `Unsigned` → `unsigned`, `Quarantined` → `quarantined` |
| `seal_status` | `SealInfo.state`: `NotSealed` → `unsealed`, `Sealed` → `sealed`, `Damaged` → `seal_failed` |
| `tiles_crc_failed` | `tiles_crc_failed` (copied) |
| `invalid_tile_indices` | Every index in `0 .. tiles_total-1` that is not a valid floor. After the other fields are filled, if `quarantine_reason` is `signer_not_pinned` or there are no valid floors, the list is every index in that range so pack `open` and a mapped `verify` agree (AT-165). If the reader cannot open the file, the list is empty. |
| `break_index` | The first tile index at which the seal chain breaks, when `SealInfo` or `checks` records one; otherwise `None`. |
| `torn_tile_indices` | Increasing indices of torn tiles (reader `tile_at` is `Err` or the tile is flagged torn). |
| `quarantine_reason` | When `status` is `quarantined`, the highest-priority applicable reason, else `None`. Priority order: `signer_not_pinned`, `missing_signature`, `seal_trailer`, `chain_break`, `signature_known_signer`, `crc`. Grounded in `SignatureCheck.detail` (including "signer key not in pinned list", "Ed25519 signature invalid", "seal hash does not match recomputed chain"), `SealInfo.state == Damaged`, and `tiles_crc_failed`. |
| `detail` | `integrity_detail` (copied) |

`SignerTrust` and `SignatureCheck` themselves are not copied as raw fields; pack `status` and `quarantine_reason` encode pinned versus embedded and the quarantine cause. `unverified` is a legal `status` value (verify has not been called) but `open_verified` returns `KiteError` for it (DD-116, DD-99). AT-165 lives in s3a-reader (feature-gated with AT-38 / AT-39 / AT-43 / AT-63) and uses this table.

The pack vendors the Kitesurf Rust core from [ashleycribb/s3a-Kite](https://github.com/ashleycribb/s3a-Kite) at `235111c6fe10f2d63f3476bf5e3d19b4c7089415`. The TypeScript engine, Wrangler, Worker Loader, and TypeScript CDP are not runtime dependencies.

`s3a-core` MUST NOT depend on this pack. The pack depends on `s3a-engine`, `s3a-edge`, `s3a-pack-scholar`, and the forked Kitesurf crates.

**Test locations and pins (DD-121).** Pack tests (AT-01–AT-37, AT-41, AT-42, AT-44–AT-62, AT-64–AT-191 except the reader-only tests below) live in a `kite-acceptance` crate in the s3a-storage workspace that is **excluded from workspace `default-members`**. `cargo test` at the workspace root does not build that crate, so the workspace stays green before `s3a-pack-kite` exists. A CI job that builds the pack also builds `kite-acceptance`. Tests that spawn `s3a-kite host` fail at **runtime** (not at compile time) if the binary is missing, with a documented "binary not found" failure. Tests must not be edited to make them pass. AT-38, AT-39, AT-43, AT-63, and AT-165 live in s3a-reader and are **feature-gated or in a separate test crate that does not build in the default reader CI job** until the reader pin moves off `ff89564` to a git revision of s3a-storage that contains `s3a-pack-kite`. AT-40 lives in s3a-storage as the iOS link gate. Path dependencies are allowed only in local developer checkouts. "Land" means local branches; nothing is pushed until Ashley says so. Android/iOS ATs run only on a job that has the NDK or Apple toolchain; they are skipped, not failed, on a host-only CI job, and the skip is reported.

### 5.2 Native host (hub, Aura Rack, LRS VM, lab PC)

The CLI is `s3a-kite host [flags...]` (DD-95). `host` is the only v1 subcommand; flags after `host` are the section 5.2.2 inventory. There is no `s3a-kite` invocation that starts the HTTP listener without `host`.

The host process:

1.  Compiles `kitesurf-core` and `renderer-core` with feature `native-host` and links them as native `rlib`s (DD-02). Wasmtime is not used in v1. Boa is not used in v1.
2.  Requires the flags in the section 5.2.2 inventory for the chosen mode. Missing required flags are an error in every mode. There is no silent port or bind default (DD-03).
3.  Rejects unauthenticated HTTP as in §5.2.1 (DD-11, DD-29, DD-71). There is no CDP listener in v1 (DD-41).
4.  For a candidate **source fetch** (select or download of a paper that has a `source_url`): the host itself performs the HTTP request, applies the egress policy in §5.2.4, and stores the raw response body as in §5.5. It does not start Boa, Wasmtime, or a page-script isolate. There is no `POST /v1/open` by URL.
5.  For `.s3a` and Edge files: the host calls `render_manifest` / warehouse / floor functions and paints `RenderFrame`s. For wiki Markdown and HTML files: the host calls `render_page`. No Boa, no Wasmtime, no page-script, and **no subresources of any kind** (network or local: no `<img>`, `<link>`, `@font-face`, or Markdown image/file includes are loaded from disk or the network) (DD-77, DD-118, AT-121, AT-167).

**Native window (DD-60).** The window is compiled behind the cargo feature `native-window` and, at runtime, is suppressed by `--headless`. A `native-window` build opens the window unless `--headless` is set. A build without the feature must pass `--headless` or startup fails and names `--headless`. The window is a Host HTTP API client in this process. It attaches the UI token to every request other than the tokenless health case. It does not call select/download/skip/consent through the pack FFI (those functions are not in the pack API). A native window is allowed only when `--bind` is a loopback address or a Unix socket; `--headless` is required for any other bind (loopback and `unix:` binds never use TLS; passing `--tls-cert` or `--tls-key` on them is a startup error that names the flag, so a windowed start must omit those flags). If `--headless` is omitted and no display is available, startup fails and names `DISPLAY`. The HTTP listener is always started.

One Scholar-mode host process serves one `--researcher-id` and one working archive. Durable local disk is required in Scholar mode (DD-48, DD-78).

#### 5.2.1 Host HTTP API (DD-42)

All routes below are the complete v1 HTTP surface. Authentication is checked first (DD-71): a missing or invalid token yields **401** on every route other than the **tokenless health case** (`GET /health` on a loopback or Unix-socket bind without `--behind-proxy`). With `--behind-proxy`, `/health` also requires a token (AT-50, AT-87, AT-113). A valid token on an unknown path yields **404**. AT-06 is "401 without a token on every route other than the tokenless health case; 404 with a valid token on a path not in this table." There is no CDP upgrade.

JSON uses UTF-8 and `Content-Type: application/json`. Errors are `{ "error": "<code>", "message": "<text>" }` with the HTTP status in the table below. `<handle>` is an opaque string minted by `/v1/open`.

Contract defaults for `/v1/frame` query parameters (DD-69), used only when the parameter is omitted: `scroll_x=0`, `scroll_y=0`, `instant=false`, `device_pixel_ratio=1.0`. `w` and `h` have no default and are required. `floor` is required for `floor-transition` and `floor-detail`. `t` is required for `floor-transition` when `instant` is false. `w`, `h`, `scroll_x`, `scroll_y`, `x`, and `y` are **CSS pixels**. The response `width` and `height` are pixmap pixels: `ceil(w * device_pixel_ratio)` by `ceil(h * device_pixel_ratio)` (§5.8, DD-90). A request whose pixmap pixel count exceeds `--max-frame-pixels`, or whose `w` or `h` is 0, or whose `device_pixel_ratio` is not a finite number greater than 0, returns `400` `invalid_frame_size` (AT-141).

**Handles (DD-74, DD-92).** `--max-open-handles` is required in both modes and must be an integer ≥ 1. `--handle-idle-secs` is required in both modes and must be an integer ≥ 1. A handle with no `/v1/frame`, `/v1/hit-test`, `/v1/proceed`, or `/v1/close` for that many seconds is closed; the next use is `404` `unknown_handle` (AT-149). A further `/v1/open` that would exceed the cap returns `429` `too_many_handles` and mints no handle. `POST /v1/close` releases a handle. On process exit, all handles are dropped. `/v1/frame`, `/v1/hit-test`, `/v1/proceed`, and `/v1/close` on one handle are serialized by the same per-handle lock. The last-frame cache, and `hit_test`'s lookup into it, are keyed by `(handle, view, floor)` everywhere (DD-125, AT-172). If no such frame exists, `hit_test` returns `409` `no_frame`.

**Write mutex (DD-102, DD-112).** Select, download, and consent are serialized by one process-wide mutex that is held **only for local disk writes** (step 0 lookup, step 1, snapshot publish, download delivery, consent-file write, retry-queue mutation, in-flight registry insert/remove). It is **not** held across the source fetch or the LRS POST. The numbered-step list in §5.5 names which sub-steps take the mutex; the fetch in step 2 does not. Skip writes nothing and does **not** take the mutex. Candidate-set membership is computed **before** the mutex is taken.

An **in-flight fetch registry** keyed by `(file_uuid, identity)` (not verb; DD-112) prevents a second GET while a fetch for that key is running. A concurrent select/download waits for the in-flight result and does not start another fetch. After the snapshot is published (or the fetch fails), the registry entry is removed. Two concurrent selects of the same identity therefore produce one tile-10 record, at most one snapshot, and **exactly one** source GET (AT-126). Snapshot files are written to a temp file in `--snapshot-dir` and published with an atomic rename.

**Process exclusivity and archive write lock (DD-114).** These are two different locks:

1.  **Process-lifetime sidecar `flock`s** (host versus host): at Scholar start the host takes an exclusive `flock` on `--data-dir/.lock` (created mode `0600` if missing), an exclusive `flock` on `--working-archive.lock` in the archive's parent directory (created mode `0600` if missing), an exclusive `flock` on `--snapshot-dir/.lock`, and an exclusive `flock` on `--download-dir/.lock` (each created mode `0600` if missing). All four are held until process exit. A second `s3a-kite host` whose `--data-dir`, `--working-archive`, `--snapshot-dir`, or `--download-dir` canonicalizes to the same path is a startup error that names the flag and binds nothing (AT-164). AT-46 uses a distinct `--data-dir`, a distinct `--working-archive`, a distinct `--snapshot-dir`, and a distinct `--download-dir`.
2.  **Engine `try_lock_exclusive` on the working-archive file** (host versus any other `TileWriter`, including s3a-cli): taken for each tile-10 write (step 1) once the file exists, and on `TileWriter::create`. This is not the sidecar lock. If an external process holds this lock, step 1 returns `500` `lock_failed` and does not truncate the file (AT-73). A second kite host never reaches this case (AT-164).

`/v1/open` of the working archive copies the file under the process-wide write mutex, so the copy cannot tear against a concurrent tile-10 append.

**Consent revoke and in-flight LRS (DD-102, DD-113).** `POST /v1/consent` `{"state":"off"}` sets an atomic in-memory consent flag to `off` **before** waiting for the write mutex. Under the mutex the host first writes `--data-dir/revoke-pending` (mode `0600`, contents `off` and an RFC3339 timestamp), then writes the consent file to `off`, then deletes `--data-dir/lrs-retry/` and finally removes `revoke-pending`. If the `revoke-pending` write itself fails, the host returns `500` `consent_write_failed`, sets the in-memory flag `off`, refuses every LRS send for the life of the process, and leaves no `revoke-pending` file (AT-189). If the consent-file write fails after `revoke-pending` was written, the host leaves `revoke-pending` in place, returns `500` `consent_write_failed`, keeps the in-memory flag `off`, and refuses every LRS send for the life of the process (AT-169). A later `POST /v1/consent` `{ "state": "on" }` in the same process returns `409` `revoke_pending` when `revoke-pending` is present; GET and the in-memory flag stay `off` (AT-181). After a failed `revoke-pending` write there is no such file, so a later POST on is not `revoke_pending`; it may attempt to write the consent file to `on`, but if that write fails the host returns `500` `consent_write_failed` and the flag stays `off`. If queue deletion fails, the host returns `500` `revoke_delete_failed`, leaves `revoke-pending` in place, consent is `off`, and the queue is not sendable (AT-124). A later POST on in that state is `409` `revoke_pending`.

On the next start, if `revoke-pending` is present, the host treats consent as `off`, retries the consent-file write and queue deletion, and does not send LRS. A failed consent-file write at that startup is a startup error that names `--consent-state-file`, binds nothing, and leaves `revoke-pending` in place. If queue deletion fails at startup while consent is `off` (including via `revoke-pending`), startup is an error that names `lrs-retry`, and the host binds nothing (fail closed).

Step 3 of select/download re-checks the in-memory flag immediately before any LRS HTTP POST (and before queueing a retry). If the flag is `off`, no request is sent and no new retry file is written. An in-flight LRS POST is aborted when the flag becomes `off` (AT-156, including a revoke during a slow LRS POST). `--lrs-timeout-secs` (required when `--lrs-url` is set, integer >= 1) bounds each LRS attempt. `--fetch-timeout-secs` bounds the **entire** source-fetch redirect chain, wall-clock from the first connect to the final body.

Opening the Scholar working-archive path via `/v1/open` succeeds: the host takes a `from_bytes` copy of the current file bytes **under the process-wide write mutex** (so the copy cannot tear against a concurrent tile-10 append) and opens that copy (DD-78).

`kind: "unsupported"` and `first_view: "banner"` are used for an unsupported stride (AT-97) or an inconsistent Edge header (AT-66). `GET /v1/frame?view=banner` (or `view=manifest`) returns the banner text in the text layer. `proceed` on those handles returns `409` `unsupported`.

**Scholar mode** is the absence of `--viewer`. **Viewer-only mode** is the presence of `--viewer`. There is no separate Scholar switch.

Select, download, skip, and consent routes return `409` `viewer_only` in viewer-only mode. In viewer-only mode, request paths are opened only under `--view-root`. In Scholar mode the allowed request roots are those in DD-89.

**Startup error precedence (DD-127).** When more than one required flag is missing or invalid, the host exits non-zero, binds nothing, and names **one** of the failing flags (no prescribed order). An AT that asserts the name of a particular flag must supply every other flag valid for that mode, so the named flag is the only error (AT-51, AT-125).

`--working-archive` names a file path. At startup the host canonicalizes its **parent directory** (the parent must exist); the file itself may be missing. The first Scholar write creates it with `TileWriter::create` and `enable_addon(ADDON_EDU)` (AT-79). `--snapshot-dir`, `--download-dir`, `--log-dir`, `--data-dir`, `--wiki-root`, `--corpus-root`, and `--view-root` must exist as directories at startup (the host does not create them). Each existing directory is canonicalized with `realpath`. A missing or non-canonicalizable required path is a startup error that names the flag.

**Disjoint write and read locations (DD-93, DD-129, AT-145, AT-179).** After canonicalization, `--snapshot-dir`, `--download-dir`, `--data-dir`, `--log-dir`, and the working-archive **parent** must be pairwise-disjoint from `--wiki-root`, `--corpus-root`, and `--view-root` (no directory is equal to or a prefix of another in the other set). `--data-dir` and `--log-dir` must also be pairwise-disjoint from `--snapshot-dir` and `--download-dir`. The working-archive parent must also be pairwise-disjoint from `--snapshot-dir`, `--download-dir`, and `--log-dir`. A violation is a startup error that names both flags. This keeps the corpus read-only, stops the recursive `*.s3a` walk from picking up snapshots, and keeps identities and logs out of request roots. Viewer-only mode applies the same disjointness between `--log-dir` and `--view-root`, and between `--pinned-keys-file` and `--view-root`. Secret and state files must not sit inside a request root (DD-129).

**Path rule (DD-89).** This rule applies to paths that come from **requests**: `/v1/open` `path`, a `Link` follow-up, and a candidate file. Those paths must canonicalize strictly inside an allowed request root, or be exactly the working-archive path (once created). A resolved `drive_path` is **not** a request path: if it is missing, cannot be canonicalized, escapes the source-table roots, or lands in `--snapshot-dir` or `--download-dir`, it is silently treated as no usable on-disk source (`on_disk: false`); the select or download is not `409` `path_escape` (AT-150). Allowed request roots are `--wiki-root`, `--corpus-root`, `--view-root`, and, in Scholar mode, `--snapshot-dir` and `--download-dir`. `..` segments, symlink escapes, and `file://` URLs outside those directories are `409` `path_escape`. Separately, the host may open its own config and state files: the token file, `--tls-cert`, `--tls-key`, `--lrs-credentials-file`, `--consent-state-file`, `--pinned-keys-file`, `--log-dir` files, and `--data-dir` files (the inclusion index and `lrs-retry/`). Those paths are not required to sit inside a request root, and **must not** sit inside one: at startup, if the canonical path of `--auth-token-file`, `--tls-cert`, `--tls-key`, `--lrs-credentials-file`, `--pinned-keys-file`, `--consent-state-file`, `--data-dir`, or `--log-dir` is inside any allowed request root, startup is an error that names both flags and binds nothing (DD-129, AT-179). `--data-dir` and `--log-dir` must also be disjoint from `--snapshot-dir` and `--download-dir` after canonicalization (a violation is a startup error naming both flags). The working-archive parent must also be disjoint from `--snapshot-dir`, `--download-dir`, and `--log-dir`. In viewer-only mode the same rule applies to `--log-dir`, `--pinned-keys-file`, the token file, and any TLS files versus `--view-root`.

**Unix-socket bind (DD-72, DD-108).** `--bind unix:/absolute/path.sock` binds a Unix domain socket at that path. `--port` must not be passed (startup error if it is). The socket's **parent directory** must exist, be owned by the process euid, and must not be group- or world-writable; otherwise startup is an error that names the path (AT-174). The socket file is created with owner euid and mode `0600`. If a file already exists at that path (a stale socket or anything else), startup is an error that names the path; the host does not unlink it (AT-163). The token is still required on every route other than the tokenless health case.

**Health, tokens, TLS, and other secrets (DD-29, DD-52, DD-68, DD-73, DD-85, DD-108).**

*   `GET /health` success is exactly HTTP 200, `Content-Type: text/plain`, body `ok\n`.
*   The token file must be a single line of at least 32 characters from the set `A-Z a-z 0-9 _ -` (the unpadded base64url alphabet), optionally ending in one `\n` or `\r\n`. The host strips that single trailing newline at load; the secret is the remaining characters. Any other whitespace, any other byte, an empty file, or a secret shorter than 32 characters is a startup error that names the file (AT-45, AT-81). Comparison is constant-time on the UTF-8 secret. The Bearer value must be exactly that secret (no added newline).
*   On Unix, these existing files must be owned by the process's effective user and have mode `0600`: `--auth-token-file`, `--lrs-credentials-file`, `--tls-key`, and `--pinned-keys-file` when that flag is set. `--consent-state-file`, if it exists at startup, must also be `0600` and so owned. A `0644` (or otherwise group/world-readable) file, or a file owned by another user, is a startup error that names the file (AT-117, AT-142). `--tls-cert` may be world-readable. v1 does not specify a Windows host.
*   Files the host **creates** under `--data-dir` (the inclusion index, `lrs-retry/` entries) and the consent file after a host write (including first-run bootstrap) are created with mode `0600` and owner euid.
*   The host never writes secrets or identifiers to `--log-dir`, stdout, or stderr: UI token bytes, LRS passwords, incoming or outgoing `Authorization` header values (including Basic to the LRS), TLS private keys, paper identities, source URLs, or `--researcher-id` (AT-117, AT-142).
*   HTTPS to `--lrs-url` (and any other non-loopback https fetch) is validated against the **process platform / webpki system root store**. v1 does not pin LRS certificates (a later DD may add pinning). Loopback `http` LRS remains allowed for tests.
*   A non-loopback, non-Unix `--bind` (including `0.0.0.0`, `::`, and a specific interface IP) requires `--tls-cert` and `--tls-key`, and requires `--headless`. TLS is **1.2 or newer** (AT-163). Passing `--tls-cert` or `--tls-key` with a loopback or `unix:` bind is a startup error that names the flag (those binds never use TLS). `--behind-proxy` is accepted **only** with a loopback bind or a Unix-socket bind (AT-87). Non-loopback plus `--behind-proxy` is a startup error. With `--behind-proxy`, every route including `/health` requires the token.

**Logs and ephemeral temp (DD-88).** `--log-dir` receives append-only lines for startup (flag *names* only, never flag values that are paths to secrets or token contents), shutdown, and error messages that obey the no-identifier rule above. There is no access log of request bodies or paper ids. The ephemeral temp directory is created with `mkdtemp` and mode `0700` under `$XDG_RUNTIME_DIR` if that variable names an existing directory, otherwise under `/tmp`, with a name prefix `s3a-kite-{pid}-`. It is deleted on a clean exit. At startup the host deletes leftover `s3a-kite-*` directories under those locations that are owned by the same euid **and** whose owning process is gone (the pid in the name is not a running process, or a flock'd marker in the directory can be taken). It must not delete a live temp belonging to another same-euid host (AT-187). The `$XDG_RUNTIME_DIR` else `/tmp` choice is an explicit contract exception (DD-88, F-29, DD-136).

#### 5.2.3 Consent file (DD-50, DD-96)

`--consent-state-file` is required when `--lrs-url` is set, and is **forbidden** when `--lrs-url` is absent (startup error that names the flag, AT-114, F-30). When `--lrs-url` is set and the consent file is **missing**, the host **creates** it as UTF-8 `off`, a newline, and an RFC3339-seconds-UTC timestamp of the create, mode `0600`, owner euid (AT-151). `off` is the privacy-safe state; this is not an invented `on` default. A present but malformed file is a startup error that names the file. `POST /v1/consent` `{ "state": "on" }` without `--lrs-url` is **reachable at runtime** and returns `409` `lrs_not_configured`; no consent file is created at any path (AT-116). `POST` `{ "state": "off" }` without a configured consent file returns `200` `{ "state": "off", "timestamp": null }` (a no-op). `GET /v1/consent` without `--lrs-url` returns `200` `{ "state": "off", "timestamp": null }`. GET and POST return the host's **in-memory** consent state, not a raw reread of a possibly stale file. The timestamp is that of the last successful host write or startup read. After `consent_write_failed` (or a failed `revoke-pending` write), the state is `off` and the timestamp is the revoke time written in `revoke-pending` (AT-181).

The file format is the exact UTF-8 tokens `on` or `off`, a newline, and an RFC3339-seconds-UTC timestamp of the last change.

The host is the only writer (including first-run bootstrap). It writes with a temp file plus atomic rename in the same directory, mode `0600`. `POST /v1/consent` is the only supported toggle after start. Mid-session outside edits are not honored (the host keeps the last state it wrote or read at startup). AT-58 uses `POST /v1/consent`, not an outside editor.

DD-12's earlier "consent on and URL missing, statement fails closed" state is **unreachable** in v6: that combination is a startup error, and the toggle is rejected at runtime.

#### 5.2.4 Egress for host fetches (DD-31, DD-49, DD-64, DD-76, DD-86)

v1 has no page subprocess. Egress rules apply to the host's own select/download fetches of a `source_url`:

*   Only `http` and `https` URLs are fetched. `file://` and any other scheme are rejected and no file is read through the HTTP client (AT-123).
*   The **deny list always applies**, including to allowlisted names and to every redirect hop (DD-64). Denied: any address that is not global unicast, including loopback (IPv4 and `::1`), IPv4-mapped forms of those ranges, `0.0.0.0/8`, `::`, RFC1918, RFC4193, IPv6 site-local (`fec0::/10`), link-local, multicast, broadcast, CGNAT `100.64.0.0/10`, NAT64 / 6to4 translated forms of the same ranges, metadata (`169.254.169.254`, `metadata.google.internal`), and the configured LRS host plus every IP it resolves to (even if that IP would otherwise be allowed). Denial is at **connect time on the resolved address**, and again on every redirect hop, before the request is sent.
*   `--egress-allowlist` is a comma-separated list of exact hostnames or exact IP literals, each optionally followed by `:port`. No wildcards. Matching uses the **effective port**: the URL's explicit port, or the scheme default (`80` for `http`, `443` for `https`). An entry without a port matches **only port 443 with scheme `https`**. An entry `host:PORT` matches either scheme at that effective port. So `host` matches `https://host/` and `https://host:443/`, but not `http://host/`, `http://host:443/`, or `https://host:8443/`. `host:443` matches `https://host/`, `https://host:443/`, and `http://host:443/`, but not `https://host:8443/`. `host:80` matches `http://host/` and `http://host:80/`, but not `https://host/` (AT-183). If the flag is set, the URL's host, scheme, and effective port (and every redirect hop's) must also appear on the list. The allowlist never overrides the deny list.
*   Loopback fixture servers used by tests are reached only when the binary is built with the Cargo feature `egress_test` and the flag `--egress-test-loopback-port <port>` is set. That flag is a **startup error** in builds without the feature (including release distributions). In an `egress_test` build it excepts only `127.0.0.1` and `::1` at that exact port. Redirects from that fixture to a denied address are still denied (AT-88, AT-109).
*   `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY` environment variables are **ignored for every host fetch**, including to an allowed `egress_test` fixture (AT-122).
*   Follow at most `--max-redirects` redirects (`--max-redirects` is a required integer ≥ 0). Exceeding it is `fetch_error` and no snapshot.
*   Only a final **2xx** response is stored. A 3xx beyond the redirect budget, or a final 4xx/5xx, is `fetch_error`; the error-page body is not snapshotted or downloaded (AT-139).
*   The stored and hashed body is the **payload after `Content-Encoding` is decoded** (`identity`, `gzip`, and `deflate` are supported). Unknown encoding is `fetch_error` and no snapshot. `--max-fetch-bytes` applies to the decoded body (AT-140). "Raw response body" in earlier wording means this decoded payload.
*   Per-fetch wall-time limit is the required `--fetch-timeout-secs` flag (DD-49). It bounds the **entire redirect chain**, from the first connect to the final decoded body. Exceeding it or `--max-fetch-bytes` aborts the fetch, writes no snapshot, and returns `fetch_error` (the inclusion record, if already written, is kept). There is no silent default. There is no page-process CPU/memory limit in v1 because there is no page process.

#### 5.2.5 Kind detection and `first_view` (DD-87)

`open`, `open_verified`, `open_path`, and `/v1/open` classify bytes as follows, in this order. The name hint is the optional `/v1/open` `name`, or the path basename.

1.  If the bytes begin with `S3A_MAGIC` (`S3A1`): apply §5.3 / §5.4. A consistent Edge file is `kind: "edge"`, `first_view: "header"`. An inconsistent Edge file, a contradictory size flag on a non-Edge stride (AT-146), or a stride that is not 4096, 8192, or 128 KiB is `kind: "unsupported"`, `first_view: "banner"`. A version-1 hyper-tile is `kind: "hyper-tile"`, `first_view: "manifest"`. A non-1 `FileHeader.version`, or magic present but a header that cannot be opened, is an error: host `/v1/open` returns `400` `invalid_magic`; pack `open` / `open_verified` / `open_path` return `Err` with engine `Invalid S3A file magic` or `Unsupported file version: {n}` (AT-69, AT-95). This is **not** `kind: "other"`.
2.  Else if the name hint ends with `.md` (ASCII, case-insensitive): `kind: "wiki"`, `first_view: "page"`.
3.  Else if the name hint ends with `.html` or `.htm`: `kind: "html"`, `first_view: "page"`.
4.  Else: `kind: "other"`, `first_view: "page"`. `render_page` shows the exact label `no text conversion in archive` and invents no title, abstract, or raster (DD-14, AT-148). This includes PDFs, extensionless download files, and a name hint ending in `.s3a` (or any other suffix) whose bytes do **not** begin with `S3A_MAGIC`. On the phone, that `.s3a`-named no-magic file is shown as `other` with that same label, not as `This is not an S3A file`.

`open(bytes)` without a name hint, and without S3A magic, returns `Ok` with `kind: "other"` and `first_view: "page"` (AT-95, AT-130). Kind detection in this section runs **before** any §5.3 "not an S3A file" error.

#### 5.2.6 View validity matrix (DD-107, DD-125)

`manifest`, `header`, and `banner` are aliases of `render_manifest` on archive kinds (`hyper-tile`, `edge`, `unsupported`). `view_mismatch` is `409` with that code. `unsupported` never leaves the first view (`proceed` is `409` `unsupported`). This matrix applies to `/v1/frame` and `/v1/hit-test`. The host evaluates the matrix **before** `no_frame`. The last-frame cache for hit-test is keyed by `(handle, view, floor)` (floor is omitted or null when the view has no floor). A warehouse `hit_test` after only a `page` or `manifest` frame is `409` `view_mismatch` or `409` `no_frame` according to this order (AT-172).

| Kind | State | `manifest` / `header` / `banner` | `page` | `warehouse` | `floor-transition` / `floor-detail` |
| --- | --- | --- | --- | --- | --- |
| `hyper-tile` | first (before proceed) | 200 | 409 `view_mismatch` | 409 `view_mismatch` | 409 `view_mismatch` |
| `hyper-tile` | warehouse | 200 | 409 `view_mismatch` | 200 | 200 (need `floor`; `t` when required) |
| `edge` | first | 200 | 409 `view_mismatch` | 409 `view_mismatch` | 409 `view_mismatch` |
| `edge` | warehouse | 200 | 409 `view_mismatch` | 200 | 200 (need `floor`; `t` when required) |
| `unsupported` | first only | 200 | 409 `view_mismatch` | 409 `unsupported` | 409 `unsupported` |
| `wiki` / `html` / `other` | page only | 409 `view_mismatch` | 200 | 409 `not_archive` | 409 `not_archive` |

### 5.3 Opening a hyper-tile `.s3a` file

1.  Open with `open` / `open_verified` / `open_path` as classified in §5.2.5. `open` and `open_verified` take a name hint, the required `max_frame_pixels`, and (for `open`) `pinned_keys`. `open_path` reads the file into memory and uses `MmapReader::from_bytes` (no path mmap in v1; DD-75), passing the path basename as the name hint and the caller's `pinned_keys`. This item applies only when the bytes **begin with** `S3A_MAGIC`. Bytes without that magic are never failed as "not an S3A file" here; they follow §5.2.5 steps 2–4. If `FileHeader.version` is not 1, or the header cannot be opened, fail as in §5.2.5 item 1 (AT-69, AT-95). If `tile_stride` is set and is neither 4096, 8192, nor 128 KiB, or a 4 KiB / 8 KiB size flag is set on a 128 KiB (non-Edge) stride, `/v1/open` returns 200 with `kind: "unsupported"`, `first_view: "banner"`, and a labeled unsupported or inconsistent-header banner; `proceed` returns `409` `unsupported`; the file is not toured as a hyper-tile (AT-97, AT-146). The FFI `open` of such a file returns `Ok` with that handle (not `Err`).
2.  **First view** is `render_manifest(handle, width, height, scroll_y, device_pixel_ratio)` (also reached as `view=banner` or `view=manifest`). If a committed, non-quarantined tile 78 is present and valid UTF-8, paint that exact stored manifest text (the same bytes as `lobby.manifest`, trimmed only as `print_tour_report` already trims). If several committed valid tile-78 tiles exist, use the first in tile order as the manifest; later tile-78 tiles still appear as ordinary floors. If tile 78 is absent, or every tile 78 is quarantined, paint a labeled "manifest absent" or "manifest quarantined" state and do not invent title/creator text. If tile 78 is present but not valid UTF-8, paint a labeled "manifest not UTF-8" state; do not invent replacement text. Long manifest text wraps to the pixmap width and scrolls with `scroll_y`; it is not silently truncated.
3.  The first view stays until `proceed_to_warehouse(handle)` / `POST /v1/proceed`. A Continue `hit_test` does **not** change handle state (DD-97, AT-152). There is no timer auto-advance. After proceed, `render_warehouse` is used. Floor-list fields (`index`, `type_id`, `record_count`, `size_bytes`, `payload_hash_short`) are taken from `MmapReader`, not from a full `tour_file` walk. `withheld_count` is computed by kite as in item 4, never by `tour_file`.
4.  Floor N detail is `render_floor_detail`. **`floor_index`, `Floor(n)`, and `?floor=` are the tile `index` of a valid floor**, not a 0-based position in the visible list (DD-82, AT-10). After invalid tiles are omitted from the valid floor list, the same tile index still identifies that floor. A request whose `floor` is omitted (where required) returns `400` `missing_param`. A request whose `floor` is present but is not the tile index of a valid floor returns `409` `invalid_floor`. The invalid-list is banner text only and is not hit-testable (AT-138).

    **Hyper-tile research-consent filter (grounded in `s3a-core` `consent.rs` and `s3a-cli` `tour.rs` `build_consent_state` / `is_record_withheld`; DD-67, DD-110, AT-11, AT-112, AT-135, AT-136).** Evaluation uses core `ConsentRecord` and marks only. The pack **must not** implement the type-82 branch in `tour.rs` (that branch is a known bug and is not a ConsentRecord). Research-purpose `ConsentRecord`s are considered in **increasing tile index, then increasing record index within the tile** (the same walk order as `build_consent_state`'s floor list). Latest-wins is **per `subject_id` only**, and only `ConsentRecord`s with `purpose == Research` enter the map (a later record overwrites the earlier `is_active` for that subject). `is_active` is `withdrawn_at == 0 && (expires_at == 0 || now <= expires_at)` as in `consent.rs`. `now` is Unix UTC seconds. Pack tests inject a clock (AT-161); the running host uses the process clock. `scope` and `study_id` exist on the record and are **not** used by this filter. **Restrict-only from invalid or unauthenticated tiles (DD-111).** Records from those tiles **can only restrict, never release**. The host builds the latest-wins `subject_research_status` **grant map** only from research `ConsentRecord`s on **authenticated valid floors**, in the walk order above. Authenticated valid floors are valid floors of a file that is not unauthenticated as a whole. A hyper-tile is unauthenticated as a whole when a seal trailer is present and `verify_sealed_archive` fails (every tile of that file is unauthenticated for this rule, even CRC-valid committed tiles that remain listed as floors under AT-90). An **unsealed** hyper-tile (`Unsigned`, `unsealed`) is **not** unauthenticated for this rule (AT-136 still applies). Individual tiles are also unauthenticated when they are not a valid floor, sit after a seal-chain break, fail a committed CRC, fail a mid-chain signature, or sit in a file Quarantined because the signer is not in a non-empty pin list. The same restrict-only rule applies to Edge type-71 records (§5.4 item 6).

It then applies, as extra restrictions only, any withdrawal or mark found in a parseable invalid or unauthenticated tile: a research `ConsentRecord` with `is_active == false` for a `subject_id` withholds **that subject only** and does **not** enter the grant map (other subjects are not flipped into filter mode) (AT-184). Withdrawn marks still withhold. A **grant** (`is_active` true) in such a tile is ignored and must not overwrite an earlier withdrawal, including a withdrawal on an authenticated valid floor or an extra-restriction withdrawal (AT-176, AT-185). A withheld payload must not appear in `text_runs`, `semantics`, pixels, or hit-test targets (AT-11, AT-23).

    *   If the grant map is empty, no withdrawn marks apply, **and** no parseable invalid or unauthenticated tile holds a research withdrawal, the tour is **unrestricted** and `withheld_count` is 0. This includes a file with no `ConsentRecord`s at all, and a file whose only `ConsentRecord`s are non-research (AT-112, AT-135). A lone invalid-tile withdrawal for subject X withholds X only; it does not make the grant map non-empty for other subjects (AT-184).
    *   If the map is non-empty, a payload record that **has** a `subject_id` is withheld unless that subject is in the map and the winning research record is `is_active`. A payload record **without** a `subject_id` is not withheld by `ConsentRecord`; it is withheld only by marks (`MARK_CONSENT_WITHDRAWN`, or `MARK_TARGET_ALL_RECORDS` as implemented in `tour.rs`).
    *   AT-136 covers a later research `ConsentRecord` that withdraws an earlier grant for the same `subject_id`: that subject's records are withheld.

    Golden fixtures are the oracle when type 82 is present. The CLI may be used as a cross-check only on hyper-tile fixtures that contain no type-82 tile.
5.  Archive bytes are painted as text, never executed as HTML or JavaScript (same policy as `tour_html.rs` escaping). No JS context is created (observed as in AT-34: `cargo tree` for the host and Android targets contains no `boa_engine` and no `wasmtime`).
6.  Animation is `render_floor_transition` (§5.8). Seal verification uses `s3a-engine` (`verify_sealed_archive` / `verify_sealed_bytes`). Labels follow the §5.4 table: an unsealed hyper-tile may be opened with `status` Unsigned and `seal_status` unsealed, and still shows the manifest or "manifest absent" state (AT-72). If `verify_sealed_archive` fails on a file that has a seal trailer, `status` is Quarantined and `seal_status` is seal_failed; CRC-valid committed tiles may still be listed as floors, but the banner reports the seal failure and no floor is presented as a verified seal (AT-90). A sealed-OK hyper-tile (trailer verifies, no device signer) is Unsigned with `seal_status` sealed, not Verified (AT-154). The host must not use the CLI's 128 KiB unsealed scanner on any file.
7.  The only open path is `from_bytes` (a snapshot of the file). Path mmap is **not used in v1** (DD-75). Open is also bounded by `--max-open-bytes` / FFI `max_open_bytes` (`409` `file_too_large` / `KiteError` when exceeded; DD-123, AT-170). A failed open is an error, not a hang.

### 5.4 Opening an Edge micro-tile file

1.  Detect with `MmapReader::is_edge_archive()` (flag or stride 4096/8192). If `FLAG_PROFILE_EDGE` is set but `tile_stride` is not 4096 or 8192, or a size flag disagrees with `tile_stride` (for example `FLAG_TILE_SIZE_4KB` with stride 8192), or both 4 KiB and 8 KiB size flags are set, do not tour as if the header were consistent: `/v1/open` returns 200 with `kind: "unsupported"`, `first_view: "banner"`, and a quarantine / "inconsistent Edge header" state (AT-66). `proceed` returns `409` `unsupported`. `tile_stride` is not silently fixed. If `FLAG_SEAL_CHAIN_ACTIVE` is clear, the file is an **unsealed Edge** file: open it, show seal status "unsealed" on the header sheet, and do not auto-quarantine solely for that flag (AT-147).
2.  Verification is performed only by `s3a-engine`. On mobile, `s3a-reader-core` may run first; kite consumes a `KiteVerificationReport` (DD-80) and does not compute a second result when that report is supplied, even if a fresh verify would disagree (AT-137). **Invalid tiles** (torn, CRC-failed, chain-broken) are omitted from the valid floor list, counted on the header sheet / banner, and may appear only in a clearly marked invalid list (banner text, not hit-testable). They are never drawn as valid floors. When the seal chain breaks, tiles before the break that already verified remain valid floors; the breaking tile and every subsequent tile are not valid floors. The banner reports the break index. `floor_index` remains the tile `index`.

    **Ed25519 and device public-key provenance (DD-57, DD-79, DD-98, DD-99, DD-100).** Type-70 tiles contain one or more `DeviceSealRecord`s. Each record's `signature` is verified with `verify_signature_raw` against a public key over that record's 32-byte `seal_hash`. The record's `tile_index` is the tile whose chain hash the signature covers. Records are considered in increasing `tile_index` order.

    The pack **must not treat a public key embedded in the file** (`DeviceIdentityRecord.public_key`, or any key carried in the same bytes) as a trust anchor. That is the same rule as `s3a-reader-core` `verify(pinned_keys)` and as s3a-vault contact pinning (`vault contact add` of a full 32-byte key; S3A-EDGE-PROFILE.md §543 "cached or provisioned public_key"):

    *   The trust anchor is the **pinned-key list** passed into `open` / `open_path` as `pinned_keys` (possibly empty). The host loads that list from `--pinned-keys-file` when the flag is set, or passes an empty list if the flag is omitted. The file, when the flag is set, is UTF-8 hex-encoded 32-byte keys, one per line, trailing newline stripped the same way as the token file; empty lines and lines starting with `#` are ignored; it must be euid-owned and mode `0600`. After comments and blanks are ignored, a remaining line that is not exactly 64 hex characters (a 32-byte key) is a startup error that names the file. Zero remaining lines is a valid empty list (the same as omitting the flag) (AT-182). The pack does not read the host flag itself. The phone app passes the same list it used (or would use) for `verify(pinned_keys)`.
    *   If the pinned list is **empty**, a signature that verifies against a key found in the file is at best **Self-signed**, never **Verified**.
    *   If the pinned list is **non-empty**, the signer must be in it or the file-level label is **Quarantined** ("signer key not in pinned list") and **no tile is a valid floor**.
    *   `FLAG_ED25519_SIGNED` set with no type-70 tile and no usable key is **Quarantined** (AT-134).
    *   `FLAG_ED25519_SIGNED` **clear**, no signatures, and a non-empty pinned list is **Unsigned** (not Quarantined) (AT-154).
    *   AT-133: a file re-signed with a different key that is not in the pinned list is Quarantined, even if the new key is embedded in a `DeviceIdentityRecord`.

    **Per-tile outcomes vs file-level label (DD-100, AT-17, AT-35, AT-155).**

    *   **Torn or uncommitted** tiles are omitted from the valid floor list, counted on the banner as ignored/torn, and do **not** by themselves make the file Quarantined (AT-17, EDGE "torn tiles are ignored").
    *   A **CRC failure on a committed** tile (hyper-tile or Edge) makes the file-level label **Quarantined**. That tile and every subsequent tile are not valid floors; earlier CRC-ok committed tiles remain valid floors (AT-35). For a hyper-tile, `seal_status` is `seal_failed` if a seal trailer is present, otherwise `unsealed`. Payload display uses only valid floors. Consent and mark records from parseable invalid or unauthenticated tiles can only restrict, never release (§5.3 item 4, DD-111).
    *   Any **seal-chain break** (`SealedChainBreak`, reordered tiles, a mid-chain signature that does not verify, or a committed CRC that breaks the chain) makes the file-level label **Quarantined** and `seal_status` `seal_failed`. Earlier tiles that already verified may remain valid floors (AT-18, AT-35, DD-111).
    *   A **signature failure from a known signer** (the signer key is in the pinned list, or the pin list is empty and the signer is the embedded device key): the tile at that `tile_index` and every subsequent tile are not valid floors; earlier tiles that already verified remain valid floors. The file-level **status** is **Quarantined** (it does not stay Verified or Self-signed); the banner reports the break index (AT-155, F-09). A later type-70 record with a higher `tile_index` does not re-validate an earlier failure. The type-70 container tile itself is not a valid data floor when its signatures fail.
    *   A mid-chain (or any) signature whose signer is **not** in a non-empty pinned list: the file is **Quarantined** and no tile is a valid floor (the signer is not a trust anchor) (AT-155 first case).

    **Verification label table (DD-99, DD-116).** `KiteVerificationReport.status` is one of `verified`, `self_signed`, `unsigned`, `quarantined`, `unverified`. `seal_status` is one of `sealed`, `unsealed`, `seal_failed`. `unverified` means verify has not been called; it is a legal report field value and is a `KiteError` from `open_verified` (AT-154). UI labels are **Verified**, **Self-signed**, **Unsigned**, **Quarantined**, plus a separate seal-status text **sealed** / **unsealed** / **seal failed**. `unverified` is never painted as a UI label (the open is rejected). Only Pinned plus a successful signature yields Verified.

    | Kind | Seal / signature situation | Pin list | `status` | `seal_status` |
    | --- | --- | --- | --- | --- |
    | Hyper-tile | No seal trailer; `verify_sealed_archive` is not applicable | any | Unsigned | unsealed |
    | Hyper-tile | Seal trailer verifies | any | Unsigned | sealed |
    | Hyper-tile | Seal trailer present and `verify_sealed_archive` fails | any | Quarantined | seal_failed |
    | Hyper-tile | Committed tile CRC failure | any | Quarantined | `seal_failed` if a trailer is present, else `unsealed` |
    | Edge | `FLAG_SEAL_CHAIN_ACTIVE` clear; no auto-quarantine for that flag alone (AT-147) | any | (from signatures below) | unsealed |
    | Edge | Seal chain active and intact | (from signatures) | (from signatures) | sealed |
    | Edge | Any seal-chain break (`SealedChainBreak`, reordered tiles, mid-chain signature failure, or a committed CRC that breaks the chain) | any | Quarantined; earlier valid floors may remain | seal_failed |
    | Edge | Signatures verify against a pinned key | non-empty, signer in list | Verified | (as above) |
    | Edge | Signatures verify against an embedded key | empty | Self-signed | (as above) |
    | Edge | Signature present from a known signer (pinned, or embedded when the pin list is empty) that does not verify | (as that known case) | Quarantined; earlier valid floors may remain | (as above) |
    | Edge | Signatures present, signer not in a non-empty list | non-empty | Quarantined; no valid floors | (as above) |
    | Edge | No signatures, `FLAG_ED25519_SIGNED` clear | empty or non-empty | Unsigned | (as above) |
    | Edge | `FLAG_ED25519_SIGNED` set, no type-70 / no usable key | any | Quarantined | (as above) |
3.  **First view:** a derived header sheet via `render_manifest` (also `view=banner`), clearly labeled as derived from the file header and `DeviceIdentityRecord`, not as a stored tile 78 manifest. Fields are only those present: magic, flags, `tile_stride`, `tile_count`, generation, timestamps (RFC3339 seconds UTC, `humantime::format_rfc3339_seconds`), `file_uuid`, device id, hardware model, firmware version, and the verification label from item 2. Missing fields are omitted, not invented. If no `DeviceIdentityRecord` is present, omit device fields and show a labeled "device identity record absent" note; still open the file (the EDGE §6.3 MUST is on the writer). If several identity records exist, the header sheet uses the first in tile order and later ones remain floors. Device identity fields on the header sheet and on type-64 identity floors are **exempt** from research-purpose record filtering: they identify the file and the device, not a consent-gated payload record (DD-53, AT-86).
4.  **Warehouse tour scaled to micro-tiles:** each committed valid micro-tile is a floor, via `render_warehouse`. `size_bytes` is 4096 or 8192. Offsets follow Variant A (`512 + i * tile_stride`) or Variant B (tile 0 at `P = tile_stride`, which is 4096 or 8192). Visual footprint follows §5.8. The Continue control on the header sheet is a `hit_test` target only; the client must call `proceed_to_warehouse` / `POST /v1/proceed` to reach the tour, same as §5.3 (DD-97, AT-152).
5.  Type 64 with 32-byte records renders as an equipment event log: timestamp (RFC3339 seconds UTC), `event_type` name from EDGE §5.2.2, severity, and a non-color category label derived from `event_type`: **fault** for `0x0003` and `0x0004`; **maintenance** for `0x0005` and `0x0006`; **normal** for `0x0001`, `0x0002`, and `0x0007`; **unknown** for any other value. Color is by severity (DD-07), which **overrides** the category coloring in EDGE §10 (a maintenance event with severity 0 uses the severity-0 color, not a category color). Color is never the only channel. Exact RGB is Q-10; AT-19 asserts pairwise-different colors plus labels. Type 64 with 96-byte records renders as `DeviceIdentityRecord` using `edge_display_layouts()`. Type 64 with `record_count` 0, or a record size that is neither 32 nor 96, is an "unknown layout" floor, not event columns and not identity columns.
6.  Edge consent uses type 71, not type 82 and not core `ConsentRecord`. Edge consent follows the same restrict-only rule as §5.3 item 4 and DD-111 (not "CRC-valid records only"). The host first considers type-71 records that sit on **valid floors**, in increasing tile index then record index; the last of those wins (DD-110). That record allows the research purpose when `(allowed_purposes & PURPOSE_RESEARCH_ANALYTICS) != 0` and it is not expired (`expires_at == 0 || now <= expires_at`), using the same injectable clock as §5.3 item 4. The latest-wins grant map is built only from type-71 records on **authenticated valid floors**. A file whose seal trailer is present and fails verification, or whose signer is not in a non-empty pin list, is unauthenticated as a whole: every tile is unauthenticated for this rule. An **unsealed** Edge file is not unauthenticated as a whole. Then any parseable type-71 **denial** (research purpose not allowed, or expired) found in an invalid or unauthenticated tile — including a CRC-failed tile, a tile after a seal-chain break, every tile of a seal-failed file, or any tile in a file Quarantined because the signer is not pinned — is applied as an extra restriction and withholds event-log payloads. A grant in such a tile is ignored and must not override an earlier denial (AT-177, AT-178). If the grant map is empty and no restrictive record appears in an invalid or unauthenticated tile, research-purpose filtering does not withhold records (AT-85). When event-log payload records are withheld, `withheld_count` is reported (AT-23); header and identity remain visible (AT-86).
7.  No transcoding into a 128 KiB hyper-tile file is required in order to view (EDGE §1.2). Import via `import_edge_archive` is a separate, existing engine operation, not the viewer path.

The microcontroller continues to run only `s3a-edge`. It does not link kitesurf or the host (AT-22, DD-06).

### 5.5 Scholar wiki browser (3-pass) — hub and PC only

Phone v1 does not implement this section (DD-45).

*   Wiki Markdown from under `--wiki-root` / `--corpus-root` is parsed with `pulldown-cmark` (raw HTML disabled or escaped) and painted with `render_page`. No JS, no remote subresources, no JS context. Missing pages are reported as missing. HTML files opened under an allowed root are also `render_page`, with JavaScript disabled and **no subresources of any kind** (network or local: a relative `<img>`, `<link>`, `@font-face`, or Markdown image/file include is not loaded from disk or the network; DD-77, DD-118, AT-121, AT-167).
*   **Current candidate list (DD-61, F-07, F-35).** There is no persisted candidate list. `GET /v1/candidates` and the membership check for select, download, and skip **recompute the set at that request**. A `paper_id` that is in the set at request time is accepted even if no prior GET listed it. A `paper_id` that is not in the set at request time is `404` `unknown_paper`, even if an earlier GET listed it (AT-105). The set is the union of:
    1.  every regular file matching the exact glob `{root}/papers/SRC-*.md` (not recursive) under `--wiki-root` and under `--corpus-root` (identity is the `SRC-NNNN` stem of the filename; if the YAML `source_id` is present and does not equal that stem, the file is omitted from the list and no paper id is written to logs);
    2.  every live (non-tombstone) `AcademicPaperRecord` in every regular `*.s3a` file found by a recursive walk of `--corpus-root`, after applying the §5.3 item 4 / §5.4 consent filter and the valid-floor rules (DD-117, AT-166). A withheld or invalid-tile record is not a candidate. A **Quarantined** corpus file contributes **no** `AcademicPaperRecord` candidates (privacy-safe: a file whose signer or seal failed does not leak identities into the list). There is **no join** of an SRC stem to a `paper_id` (v4's "already the same paper" wording is deleted; there is no grounded join key). If the same `paper_id` appears in more than one live, un-withheld record in a non-quarantined file, keep one: sort the containing `.s3a` paths, then take the first record in tile order in the first of those files. The walk **does not follow symlinks** (a symlink file or directory is skipped, not opened, and not descended). Files that fail to open are skipped. A file larger than `--max-open-bytes` is skipped as a fail-to-open. A dossier whose YAML front matter is missing, unparseable, or not UTF-8 is **omitted** from the list and no paper id is written to logs (AT-188). The cost of a fresh walk is acknowledged; an implementation may cache results keyed on `(canonical path, mtime, size)` provided the observable result equals a fresh walk after any of those values change. Membership for select/download/skip is computed before the write mutex is taken.
    If the same relative path `papers/SRC-XXXX.md` exists under both roots, **`--wiki-root` wins**; there is one candidate. Building the list twice writes nothing (AT-24). Each candidate includes `title` (dossier YAML `title` if present; the empty string for `AcademicPaperRecord` candidates), `source_url` (from the optional YAML key `source_url` **only** when it is a valid `http` or `https` URL, else `null`) and `on_disk` (true when a usable local file exists; see the source decision table). A `file://`, `data:`, or other non-`http`/`https` value is stored as `null`. The host does not HTTP-fetch that value and does not read the `file://` target from the filesystem. If that candidate also has no usable `drive_path`, download is `no_source`. Such a file is opened only via `/v1/open` of a path under an allowed root (AT-55, AT-123).
*   **Source decision table (DD-59, F-06).** A dossier `.md` file is **not** itself the on-disk source. On-disk bytes, when present, come from a `drive_path`:
    *   an absolute `drive_path` must canonicalize inside `--wiki-root`, `--corpus-root`, or `--view-root` if set, and **not** inside `--snapshot-dir` or `--download-dir`;
    *   a relative `drive_path` is resolved against the **parent directory of the dossier file**, then must canonicalize inside one of those allowed roots, and **not** inside `--snapshot-dir` or `--download-dir`.
    A `drive_path` that is missing, cannot be canonicalized, escapes those allowed roots, or canonicalizes inside `--snapshot-dir` or `--download-dir` is not a usable on-disk source (`on_disk: false`); select and download of that candidate are not `409` `path_escape` (AT-150). `--snapshot-dir` and `--download-dir` hold kite-written artifacts; they remain allowed `/v1/open` roots in Scholar mode.
    A Windows Google Drive path, or any other `drive_path` that does not so canonicalize, is not an on-disk source (`on_disk: false`); select and download of that candidate are not `409` `path_escape` (AT-150). Remote bytes, when present, come from the optional front-matter key `source_url` (draft name; not present in the grounded 3Pass tree; fixtures and future dossiers may set it). `AcademicPaperRecord` typically has neither a `source_url` nor an on-disk file. `POST /v1/open` does not accept a URL. At select/download:

    | `source_url` | usable `drive_path` | Fetch | Snapshot | Download delivery |
    | --- | --- | --- | --- | --- |
    | yes | no | yes (unless a snapshot already exists for this identity in the current archive, any verb) | yes, on 2xx decoded body | bytes from the snapshot BLOB tiles |
    | no | yes | no | no | copy of the on-disk file |
    | yes | yes | no (prefer on-disk) | no | copy of the on-disk file (AT-129) |
    | no | no | no | no | `200` with `path: null`, `download_error: "no_source"`; inclusion and index still written (AT-128) |

    Fetch is triggered only by select or download of a request-time candidate in the first row of that table. Select and download share one fetch: if a snapshot already exists for the identity in the current working archive, or a fetch for that `(file_uuid, identity)` is already in flight (DD-112), download does not start a second GET and either waits for the in-flight result or reassembles bytes from that snapshot's BLOB tiles (DD-61, AT-104, AT-126).
*   Pass 1 list and skip write nothing. The 15-second timer may be shown in the native UI; it is client-side; expiry does not call a host write endpoint (DD-08). AT-29 waits 15 seconds after only `GET /v1/candidates`, `POST /v1/open`, and `GET /v1/frame` and checks byte-identity of the working archive, `--snapshot-dir`, `--download-dir`, `--data-dir`, and `--log-dir`.
*   **Numbered write steps (F-05, DD-84, DD-120).** Select and download share this order. The process-wide write mutex is held only for the disk sub-steps named here; it is released before a fetch or LRS POST and re-acquired for the next disk sub-step.
    Step 0, step 1, and the in-flight registry check-or-insert run in **one** mutex hold (DD-102). The verb is used only for inclusion-record idempotency. Snapshot existence and the in-flight registry are keyed by `(file_uuid, identity)` (DD-112).
    0.  (mutex, with 1 and the registry) Look up the last matching inclusion-index line for `(file_uuid, identity, verb)`. If a matching line is present, skip step 1. A snapshot already exists if any index line for this `(file_uuid, identity)` (any verb) has a non-null `snapshot_sha256`. Run step 2 only if no such snapshot exists and the source table requires a fetch; if a fetch is required, check-or-insert the in-flight registry in this same hold. Run 2b for a download request. If a matching verb line was present, do **not** emit a new LRS statement (step 3 is skipped).
    1.  (same mutex hold) Write the inclusion record (tile 10) and append the inclusion-index line (including a null `snapshot_sha256` if no snapshot exists yet).
    2.  If the source table requires a fetch and no snapshot exists for `(file_uuid, identity)`: if the registry shows a GET for this key is running, wait for its result (mutex released during the wait for a GET already started by another request); otherwise start one GET (mutex released across the GET). Then, under the mutex, write the snapshot (temp file + fsync + atomic rename) if this request started the GET, and **append a new index line** with the snapshot SHA-256 (the index is append-only; there is no in-place rewrite).
    2b.  For a download request only: (mutex) deliver bytes into `--download-dir` via temp + fsync + rename (copy, or reassembly from the snapshot). If reassembly from a snapshot fails, `download_error` is `"snapshot_invalid"`, no file is written in `--download-dir`, and the inclusion record is kept (AT-180).
    3.  If consent is `on` at the pre-send check, emit the LRS statement (no mutex across the HTTP POST). After the POST returns, re-acquire the mutex to record the outcome. A 2xx, or a `409` on a replayed statement `id`, is success (`lrs_status: "sent"`) (DD-134). A 408, 429, or 5xx is queued only if the consent check **inside this same mutex hold** is still `on`; if the flag is `off`, write no retry file and return `lrs_status: "skipped"` (AT-156). Any other 4xx is a permanent failure: log it, keep a diagnostic file that is never retried, and return `lrs_status: "failed"`.

    If step 1 fails, skip 2, 2b, and 3, and leave `--download-dir` unchanged (AT-89, AT-127). The earlier DD-56 sentence that kept a download after a failed inclusion is **deleted**; it is unreachable once 2b follows 1. If the fetch fails or times out after step 1, the inclusion record is kept, `snapshot` is `null`, `fetch_error` is set, `download_error` is `"fetch_failed"` on a download, 2b is skipped, and step 3 is still attempted if consent is on at the pre-send check (`EXT_CONTENT_SHA256` is present if and only if the index has a non-null `snapshot_sha256` for `(file_uuid, identity)` at step 3, and is equal to it). A fetch is not started when a snapshot already exists for the identity. A repeat whose index line has a null `snapshot_sha256` and whose source table requires a fetch retries the fetch (AT-186).
*   Tracing consent on/off, and "zero LRS requests when off", are enforced including on retries (DD-66). Consent toggling is only `POST /v1/consent` (DD-50).
*   Only a UI-token `POST /v1/select` or `POST /v1/download` creates an inclusion record (DD-32, DD-60). "Human select" means "a call authenticated with the UI token", including one made by the native window. AT-28 tests an unauthenticated (401) call.
*   Pass 1 list and skip never write paper ids or URLs into `--log-dir`, and none into `--data-dir` other than `inclusion-index.jsonl`. The retry queue under `--data-dir/lrs-retry/` may hold identities only when consent is on and a sendable statement exists. Render caches and per-request temp files live in the ephemeral directory of §5.2.2, not under `--data-dir` or `--log-dir`. (AT-61; F-01: the index is local research data, like the working archive, and stays in `--data-dir`.)

**Inclusion record (DD-46, DD-61).** Tile 10 `HumanLrsRecord`: `timestamp_sec` is the write time (Unix seconds); `actor_hash` is `hash_iri(--researcher-id)` as implemented in `s3a-pack-scholar` `xapi.rs` (FNV-1a 64-bit; the field is `u64`); `verb_id` is the id of the existing `xapi.rs` verb chosen in Q-07; `object_hash` is CRC32C of the UTF-8 paper identity, stored in the `u32` field (CRC32C is already used in S3A); `decision_score` is 0; `ai_trace_coord` is the default / empty coordinate; flags are `FLAG_ACTIVE`. Because a 32-bit CRC is not a unique pointer to a path or identity, **idempotency is not evaluated from `object_hash` alone.**

**Inclusion index (F-01, F-02, F-03).** `--data-dir/inclusion-index.jsonl` is local research data in `--data-dir`. Each successful inclusion appends one JSON object:

```
{"paper_identity":"<id>","verb_id":<n>,"object_hash":<n>,"timestamp_sec":<n>,"working_archive":"<canonical path>","file_uuid":"<hex of FileHeader.file_uuid>","snapshot_sha256":"<lowercase hex or null>"}
```

The idempotency key is **current working-archive `file_uuid` + paper identity string + verb id**, looked up among index lines whose `file_uuid` equals the open archive's `FileHeader.file_uuid`. Lines whose `file_uuid` or canonical `working_archive` path do not match the open archive are **non-matching** and do not suppress a new inclusion (a deleted and recreated archive has a new `file_uuid`). `snapshot_sha256` is null until a successful snapshot exists. The index is **append-only**: a later successful step 2 appends a new line with the same identity, `file_uuid`, and verb and the new `snapshot_sha256`. Lookup uses the **last** matching line (DD-104). An idempotent second select of an identity that already has a snapshot returns `200` with `ok: true` and `snapshot` set to `--snapshot-dir/{snapshot_sha256}.s3a` (AT-83). A later download of that identity reassembles bytes from the snapshot BLOB tiles and does not fetch again.

Each index mutation copies the current file (or starts empty), appends the new line, `fsync`s, and publishes with an atomic rename, mode `0600`. There is no in-place rewrite of a JSONL line.

If the index file is **missing** at startup, the host creates an empty one (mode `0600`) and does **not** skip writes based on existing tile-10 `object_hash` values (duplicates of older records are possible; dropping a real inclusion is not). Creating the empty file is an explicit contract exception (F-29). If the index file is **present but malformed** (not UTF-8, a non-JSON line, a partial last line, or a line missing a required key), startup is an error that names the file; the host does not truncate, skip, or invent recovery (AT-158).

Step 1 order is: write the tile-10 record, then append the index line. If the index append fails after the tile-10 write, the response is `500` `write_failed` and the record is kept. A later select may then write a second tile-10 (the same duplicate policy as a missing index). The phrase "the inclusion record points at a path" is not used: the index stores the identity string, the archive identity, and the optional snapshot digest.

**Idempotency (DD-34, Q-07).** Selecting the same paper twice with the same verb against the same archive `file_uuid` writes one record and at most one successful snapshot. The v5 draft for Q-07 remains **one existing verb for both select and download**, so select-then-download is also one record (AT-83). If Ashley later picks two verbs, select-then-download writes two records; AT-83 follows the accepted mapping. Idempotency applies only to **successful** artifacts: a failed snapshot is retried by a later select/download of the same paper (AT-186).

**LRS client (DD-65).** When `--lrs-url` is set, the host POSTs to `{lrs-url}/xapi/statements` ( `--lrs-url` is the origin, with no trailing `/xapi`; the host appends `/xapi/statements`). `--lrs-url` must use `https`, except `http` is allowed when the host is loopback (for tests). The request uses HTTP Basic from `--lrs-credentials-file` (the s3a-lrs-server format: lines `user:password[:scopes[:archive]]`; `#` comments and blank lines ignored; kite uses the first credential line). Each credential line is parsed exactly as `s3a-lrs-server` `load_credentials_file` at s3a-storage `b7bdcda` (`main.rs`): the line is split on every `:`. `parts[0]` is the username and `parts[1]` is the password; `parts[2]` (scopes) and `parts[3]` (archive), if present, are ignored by kite. A password cannot contain `:`. A line with fewer than two fields, or with an empty username or empty password, is a startup error that names the file. After comments and blank lines are ignored, a file with no credential line is a startup error that names the file (AT-182). The request also sends `X-Experience-API-Version: 1.0.3` and `Content-Type: application/json`. The body is one xAPI 1.0.3 statement:

*   `id`: a UUID generated at first emit and stored in the retry-queue file, reused on retry (so a replay is the same statement).
*   `actor`: `{ "objectType": "Agent", "account": { "homePage": "<--lrs-actor-homepage>", "name": "<--researcher-id>" } }`. The LRS therefore sees the researcher id; `actor_hash` in the local tile does not anonymize the statement (privacy is the researcher's consent).
*   `verb.id`: the Q-07 IRI from `xapi.rs`.
*   `object.id`: the candidate `source_url` if present; otherwise `https://ashecribb.dev/xapi/activities/paper/` plus the percent-encoded paper identity. That host is already used by Scholar verb and extension IRIs in `xapi.rs`; this spec does not mint a new host.
*   `object.definition.extensions` includes `EXT_PAPER_ID` (the identity). It includes `EXT_SOURCE_URL` when a `source_url` exists. `EXT_CONTENT_SHA256` is present if and only if, at step 3, the inclusion index has a non-null `snapshot_sha256` for `(file_uuid, identity)`, and the extension value equals that digest (DD-137). An on-disk-only download with no snapshot omits it.
*   `timestamp`: RFC3339 seconds UTC of the inclusion write.

AT-110 asserts this shape. A batch of several statements may be sent as a JSON array, per xAPI, but v1 retries are one statement per request.

**Retry queue (DD-51, DD-66).** Queued LRS statements live on disk under `--data-dir/lrs-retry/` (one file per statement, including the statement `id` and body, mode `0600`) and survive a host restart. **Every LRS send, including a startup retry, first checks that the in-memory consent state is `on`.** If consent is `off` at process start, the host deletes the queue and issues zero LRS requests (AT-111). Revoke (`POST /v1/consent` to `off`) deletes that directory. If deletion fails, the host returns `500` `revoke_delete_failed`, treats the queue as **not sendable** (a send barrier until the directory is gone), and still records consent as `off` (AT-124).

HTTP outcomes (DD-134, AT-191): any 2xx is success; a `409` on a replayed statement `id` also counts as success (xAPI replay). 408, 429, and 5xx are queued for retry. Any other 4xx is a permanent failure: log it, keep the queue file, and never retry that file. Replay is serialized: under the write mutex the host **claims** a queue file (rename or equivalent exclusive claim) before releasing the mutex to send; two retries must not POST the same statement concurrently. Writing a new retry file, and the consent check that allows that write, run in the **same mutex hold** (AT-156). If consent is `off` in that hold, the host writes nothing and the caller's `lrs_status` is `"skipped"`.

Backoff and a maximum attempt count are Q-09; until Ashley sets them, the host retries at process start (only if consent is `on`) and after each later successful LRS emit, and surfaces a visible error after a failed attempt without dropping a sendable (non-permanent) queue file.

### 5.6 Write path and sealed snapshots

**Target (DD-27, DD-103).** Inclusion records go to `--working-archive`. Snapshots go in `--snapshot-dir` as `{lowercase hex SHA-256 of the captured bytes}.s3a`. If that path already exists, the host **does not overwrite it**. Before reuse it opens the existing file, runs `verify_sealed_archive`, and checks that the archive holds BLOB chunks whose `blob_key` equals that SHA-256 and that reassemble to bytes hashing to that SHA-256. If every check passes, the existing file is reused, its PROVENANCE document (the first capture's `url` and `captured` time) is left unchanged, and both identities' index lines store the same `snapshot_sha256` (AT-157). If any check fails, the host returns `409` `snapshot_conflict` with `included: true` when step 1 already succeeded, keeps the inclusion record, and does not overwrite the file (AT-180). Two `source_url`s that return identical bytes therefore share one snapshot when the existing file verifies. The corpus and wiki are read-only. The snapshot directory is an allowed open path, so AT-31's re-open is allowed.

**API and locking (DD-28, DD-102, DD-105, DD-114).** `TileWriter::create` / `open_append` use the engine `try_lock_exclusive` on the working-archive file for each write (DD-114 lock 2), in addition to the process-lifetime sidecar `flock`s held since startup (DD-114 lock 1). `ADDON_EDU` is set on create; fail closed if an existing file lacks the bit. On `create`, kite also writes one core `ConsentRecord` using `ConsentRecord::new` with every field set as follows (AT-79, AT-159, AT-173):

*   `subject_id` = `actor_id_to_subject_id(hash_iri(--researcher-id))` (the helper in `s3a-core` `consent.rs`; `hash_iri` is the same FNV-1a `u64` as `actor_hash`).
*   `study_id` = 0
*   `purpose` = `ConsentPurpose::Research`
*   `scope` = 0 (all)
*   `granted_at` = Unix UTC seconds of the create
*   `expires_at` = 0 (no expiry)
*   `withdrawn_at` = 0
*   `legal_hold` = 0
*   `_reserved` = seven zero bytes
*   `granted_by` = `hash_iri(--researcher-id)`
*   `prev_consent_hash` = 32 zero bytes (first record)
*   `consent_hash` = `ConsentRecord::compute_hash` over the preceding 104 bytes (as `new` already sets)

`HumanLrsRecord` has **no** `subject_id` field. Inclusion records are therefore not withheld by `ConsentRecord` (they are withheld only by marks, §5.3 item 4). The create-time record is an archive-level research grant for the researcher's `subject_id`, so any later payload record that *does* carry that subject remains granted. Because the grant puts a non-empty `subject_research_status` map in place, a payload record that carries a **different** `subject_id` is withheld (the filter-mode side effect of §5.3 item 4; AT-173). It is not required for visibility of a file that has **zero** consent records before create (DD-67). AT-79 requires `withheld_count == 0` for the owner's inclusion records.

**Atomic publish and temp cleanup (DD-122).** Snapshot and download files are written to a temp file in `--snapshot-dir` or `--download-dir` respectively, `fsync`ed, and published with an atomic rename. Temp names are `s3a-kite-tmp-{pid}-*` in that directory. A temp path is not openable via `/v1/open` (`409` `not_regular_file`). At startup the host deletes stale `s3a-kite-tmp-*` entries in those directories that are owned by the process euid **and** whose owning process is gone (the pid in the name is not a running process, or a flock'd marker can be taken). It must not delete a live temp belonging to another same-euid host (AT-187). Concurrent select/download/consent disk writes are serialized by the process-wide write mutex and de-duplicated by the in-flight fetch registry (AT-126). Skip does not take the mutex.

**DD-63 retired (F-22).** v4's "kite-written snapshot exemption" is deleted. A BLOB+PROVENANCE-only snapshot contains no `ConsentRecord`, so DD-67 already leaves it unrestricted. Research-purpose filtering is never skipped merely because a file sits in `--snapshot-dir`. A third-party archive copied into `--snapshot-dir` is filtered by the same §5.3 / §5.4 rules as any other file (AT-107, AT-108).

**Snapshot encoding (DD-47, F-33).** Captured bytes are stored in core BLOB tiles (68) using the 40-byte prefix in `docs/spec/registry.md` / `s3a-pack-clean` `chunk_tiles`: `blob_key` (32-byte SHA-256 of the **complete** captured bytes), little-endian `chunk_index`, little-endian `total_chunks`, then chunk data. Each tile payload is at most `HYPER_TILE_PAYLOAD_SIZE` bytes, so each chunk is at most `HYPER_TILE_PAYLOAD_SIZE - 40` bytes. Reassembly concatenates chunks `0 .. total_chunks-1` of the same key. The "payload hash" in AT-31 is that SHA-256; it must equal `blob_key` and SHA-256 of the reassembled bytes. A payload larger than 128 KiB is required in AT-82.

PROVENANCE tiles (72) use the same chunk layout. The reassembled provenance **document** (after the 40-byte prefix) is exactly the UTF-8 bytes

```
sha256=<lowercase hex>
url=<source_url>
captured=<RFC3339 seconds UTC>
```

with LF line endings and a final newline. `url=` is followed by the `source_url` (this document is written only for a fetched snapshot, which always has a URL). There is no "or empty" alternative. `blob_key` of the PROVENANCE tile is the SHA-256 of that document (not of the captured content). Kite seals with `seal_archive` (no seal-generated tile-78 requirement). If a seal manifest is later added, it is the archive's ordinary stored manifest and is not counted against AT-32.

On-disk wiki or corpus sources are not re-snapshotted. Skip does not snapshot and does not write an inclusion record.

**Download names (DD-62).** The destination path is `--download-dir/{lowercase hex SHA-256 of the delivered bytes}` with no added extension (the bytes are the authority). Sanitization is unnecessary because the name is hex only. If that path already exists and the existing file's SHA-256 equals the name, download is a **success no-op** (the path is returned, the file is not overwritten). If a file exists at that path whose contents do **not** hash to the name (a planted or corrupt file), download fails with `409` `download_conflict` with `included: true` in the error body when step 1 already succeeded, does not overwrite, and the inclusion write is kept (AT-94, AT-106). A `no_source` download writes no file in `--download-dir`.

### 5.7 Mobile build (Android, then iOS)

s3a-kite is the **viewer** inside [s3a-reader](https://github.com/ashleycribb/s3a-reader), as a UniFFI library from `s3a-pack-kite`. The phone is not a literature-review surface (Ashley, 2026-11-16, DD-128). v1 phone builds are an S3A / Edge-tile viewer: no Scholar 3-pass flow, no candidate list, select, download, inclusion, snapshots, consent, LRS, or `paper_identity` (DD-45). Those stay on the hub/PC host. v1 phone UniFFI exports `KiteContext::new`, `open`, `open_verified`, `close`, `proceed_to_warehouse`, the render functions, `hit_test`, and the `KiteVerificationReport` type (AT-99, DD-80, DD-109, F-04). It does not export `open_path`, `paper_identity`, or any Scholar write. There is no phone Scholar Explorer. AI Teacher's Assistant chat and phone paper search are future, unbuilt, and out of scope for this spec (Q-15, Q-16); this spec adds no ATs, exports, or interfaces for either. The pack does not depend on `s3a-reader-core`; the app may map a post-verify reader-core `VerificationReport` into `KiteVerificationReport` before calling `open_verified`. Pack `open` (the host always uses this) and a mapped reader-core `verify` must agree on `status`, `seal_status`, `invalid_tile_indices`, `break_index`, `torn_tile_indices`, and `quarantine_reason` (DD-115, AT-165). Drop of a UniFFI handle also releases the archive.

**Why this is feasible without a mobile GPU.** Kitesurf already rasterizes on the CPU through `vello_cpu` / `VelloCpuImageRenderer` to an RGBA pixmap. The mobile library paints the manifest, warehouse, and page into a CPU buffer and hands pixels plus the text layer to the UI toolkit. v1 does not add a wgpu or platform GPU backend (DD-21). `cargo tree` for Android and host targets must not include `wgpu` or a Vulkan / Metal / GLES backend at all, not only "on the tour path" (AT-41).

**Fonts (DD-22, DD-35, DD-101).** Keep `system_fonts: false`. There is no process-global font set. `KiteContext::new(ua_fonts)` takes the UA font bytes (Noto Sans, Italic, Serif, Mono, and Symbols). Missing those required UA fonts, or an empty set, is a `KiteError`, not a fallback to device or host fonts (AT-42). AT-42 is a library-level test of `KiteContext::new` with an empty set on the same crate the host links (DD-121). The shipped host and mobile binaries pass the required UA font bytes embedded with `include_bytes!` at startup. There is no test-only cargo feature that compiles the host without the bytes. Noto Color Emoji and Noto Sans SC are optional **bundled asset packs** (Play Feature Delivery, or a sideloaded asset packaged with the APK). They are not fetched over the network. The no-network Android manifest stays in force. ### 5.8 Render API, warehouse scale, and animation

Every paint function returns a `RenderFrame`, not only pixels (DD-38):

```text
RenderFrame {
  rgba: [u8],           # packed RGBA, length = width * height * 4
  width: u32,
  height: u32,          # pixmap pixels; at scale 1.0, 1 CSS px = 1 pixmap px
  text_runs: [TextRun],
  semantics: [SemanticNode],
}
TextRun { text: String, x: i32, y: i32, width: u32, height: u32 }   # pixmap coordinates; x/y may lie off-pixmap
SemanticNode {
  role: String,         # one of: document, heading, button, label, link,
                        # floor, continue, select, paragraph
  label: String,
  x: i32, y: i32, width: u32, height: u32,  # CSS pixels, same space as hit_test x/y and the request's CSS w/h (DD-124, AT-168)
  href: Option<String>,       # set when role is link
  paper_id: Option<String>,   # set when role is select
  floor: Option<u32>,         # set when role is floor
}
```

Acceptance tests that assert on "text" use concatenated `text_runs` as contiguous substrings, never OCR. TalkBack and VoiceOver read `semantics`.

Every `render_*` takes `width`, `height`, and `device_pixel_ratio` (DD-69, DD-90). `width` and `height` are **CSS pixels**. The pixmap is `ceil(width * device_pixel_ratio)` by `ceil(height * device_pixel_ratio)` pixels; `rgba` length is pixmap width × pixmap height × 4. `device_pixel_ratio` must be a finite number greater than 0. The product of the pixmap dimensions must be ≤ the required `max_frame_pixels` passed to `open` / `open_verified` / `open_path`, or, on the host, the required `--max-frame-pixels`. A request that violates this, or whose CSS `width` or `height` is 0, is `400` `invalid_frame_size` (AT-141, AT-143). At `device_pixel_ratio = 1.0`, 1 CSS px = 1 pixmap px (DD-37). `/v1/hit-test` `x`/`y` are CSS pixels in the same space as `width`/`height` and as `SemanticNode` `x`/`y`/`width`/`height` (AT-168 covers a `device_pixel_ratio=2` hit-test using CSS coordinates). The same defaults as `/v1/frame` apply when an FFI wrapper omits scroll / instant / dpr, and those defaults are part of the contract: `scroll_x=0`, `scroll_y=0`, `instant=false`, `device_pixel_ratio=1.0`. `select` semantics are present only when `select_enabled` is true (`render_page(..., select_enabled)`; false on a viewer-only host and on mobile; AT-144).

**`instant` (AT-13, AT-93).** When `instant` is true, `render_floor_transition` returns only the end frame (the t = 0.45 layout) and ignores `t_seconds`. When `instant` is false, `t_seconds` is used as below.

**Scale (DD-37, DD-70, AT-16, AT-92, AT-120).** At reference scale 1.0, bays are square. Side lengths are the nearest integer to `32 * sqrt(stride / 4096)` CSS px, so area is only **approximately** linear in stride. Specified integer sides: **32** (4 KiB), **45** (8 KiB, nearest integer to 32√2), **181** (128 KiB, nearest integer to 32√32). AT-16 and AT-92 render the 4 KiB and 8 KiB fixtures **separately** and assert those integer sides; they do not assert exact area doubling. AT-120 uses a 128 KiB fixture and asserts side 181. Mixed-stride warehouses are out of v1 (a file is either Edge 4 KiB, Edge 8 KiB, or hyper-tile 128 KiB). The warehouse is a scrollable grid; `scroll_x` / `scroll_y` reach floors that do not fit the viewport. Floors are not automatically shrunk below the reference scale.

**Animation (DD-18, DD-37, AT-62).** Viewport units map to the frame arguments: `1vw = width / 100`, `1vh = height / 100`. `render_floor_transition` and `/v1/frame?view=floor-transition` take `scroll_x` and `scroll_y`: the warehouse scroll at click time (default 0 only if omitted). The start rectangle is the bay's layout rectangle in frame coordinates at that warehouse scroll (it may lie partly or wholly outside `[0, width] × [0, height]`; the pixmap still only contains in-viewport pixels). Without `instant`, the floor-to-detail card starts at t = 0 on that start rectangle at opacity 0.2, and at t = 0.45 s is at `left = 0.06 * width`, `top = 0.08 * height`, `width = 0.88 * width`, `height = 0.84 * height`, opacity 1, showing **floor-detail content** in the card (not an empty card). Progress between those endpoints, including opacity, is the y-value of CSS `cubic-bezier(.2,.8,.2,1)` at unit time `t / 0.45` (at `t = 0.225` s, unit time 0.5, progress is approximately 0.946, so opacity is `0.2 + 0.8 * progress`, approximately 0.957). `t` is clamped to `[0, 0.45]`; values outside that range are not an error. Tests sample t = 0, 0.225, and 0.45 and check opacity within 0.02 of those values (AT-62). An off-screen bay still animates from its (possibly off-pixmap) start rect to the end rect.

### 5.9 Robustness

`cargo-fuzz` target `open_and_render` (AT-71) is required, with a **checked-in seed corpus** and a **corpus-replay** CI job that runs every seed to completion (not only a timed fuzz). A timed fuzz duration for CI is Q-14; this spec does not invent a duration. Malformed input is an error or quarantine, not a crash.

## 7. Acceptance tests

Tests are written first. They are split into two classes:

*   **Fail-first.** A concrete check that does not hold on today's trees (no `s3a-pack-kite` / `s3a-kite` host / UniFFI kite renderer, or the behavior is not implemented). Implementation must make these pass **without editing the tests**.
*   **Guards.** Checks that already hold on today's trees, or that become meaningful once the pack exists and must then stay green. They are not claimed to fail first. AT-22 and AT-37 already pass today. AT-05, AT-36, and AT-41 are written so that, until the host or pack crate exists, they are skipped as guards (they do not "pass vacuously" by asserting nothing); once the subject exists, they must pass.

Fixtures: hyper-tile archives built the same way as `crates/s3a-cli/tests/tour_tests.rs` (`write_manifest: true` for AT-08); Edge vectors `micro_valid_4kb`, torn and signed vectors from `s3a-spec-vectors`; an 8 KiB file produced with `EdgeWriter<_, 8192>`. Text assertions use the text layer in §5.8 and must match the fixture bytes as contiguous substrings of concatenated `text_runs` (not only a fuzzy OCR of the pixmap).

Mechanical helpers: AT-03 diffs the vendored Kitesurf tree against pin `235111c6fe10f2d63f3476bf5e3d19b4c7089415` and greps each changed file for the change notice. AT-36 uses `cargo deny` (or equivalent) bans plus a grep on pack-owned source only, not the entire vendored upstream tree.

Negative write tests (AT-28, AT-46, AT-57, AT-73, AT-74, AT-89, AT-94, AT-105) first run a **control** select that succeeds on a valid `ADDON_EDU` working archive in the same harness, then run the failing case, then assert the failing target is unchanged (or, for AT-89, that no snapshot was created). AT-46 uses a **second host process** whose `--working-archive` and `--data-dir` are distinct from host A's (one process serves one archive, DD-48, DD-114). Same-path second starts are AT-164.

Host-spawn acceptance tests live in the `kite-acceptance` crate, which is excluded from the workspace `default-members` (DD-121). Those tests fail at runtime if the `s3a-kite` binary is missing; they are not skipped as a green default. Pack unit and library tests live in the s3a-storage workspace. AT-38, AT-39, AT-43, AT-63, and AT-165 live in s3a-reader and are feature-gated or in a separate test crate that does not build in the default reader CI job until the reader pin moves off `ff89564`. Android and iOS ATs are skipped, not failed, on a host-only CI job, and the skip is reported. "Land" means local branches; nothing is pushed until Ashley says so. AT-76 is exempt from the same-process control-select requirement (a viewer-only host cannot select); any control write for AT-76 runs on a separate Scholar host.

Scholar start with `--bind 127.0.0.1` (or `unix:/path.sock` with a legal socket parent) plus `--tls-cert` or `--tls-key` is a startup error that names the TLS flag and binds nothing. `--bind 0.0.0.0` or a specific interface IP without `--tls-cert` and `--tls-key` (and without `--behind-proxy`) is a startup error. `--bind ::` is accepted as an IP literal and follows the same non-loopback TLS rule.
*   **AT-191** (fail-first). An LRS fixture that returns `409` for a replayed statement `id` is treated as success (`lrs_status: "sent"`; the statement is not retried). A fixture that returns `400` (not 408 or 429) is a permanent failure: `lrs_status: "failed"`, the diagnostic file is kept, and a later retry pass does not POST that statement again. A fixture that returns `503` is queued and retried.

## 10. Risks

1.  **`native-host` is a thin feature flag.** Much of Kitesurf's DOM and JS is `#[cfg(target_arch = "wasm32")]`. The tour and JS-disabled HTML layout path should use paint/layout entry points that already have native-host or non-Wasm coverage (`scene_replay`, `VelloCpuImageRenderer`). Additional native entry points may still be needed in the fork.
2.  **Wasm-oriented dependencies.** Workspace `getrandom` uses `js` / `wasm_js`. `fonts.rs` uses `wasm_bindgen`. Android and iOS builds fail until the pack forks those bits (AT-44), even though Wasmtime and Boa themselves are out of v1.
3.  **Today's `s3a-cli tour` is not a drop-in Edge tour.** It steps 128 KiB tiles and has a type-82 consent *branch*. Kite must use `MmapReader` for all file types, compute `withheld_count` itself, and must not build the warehouse walk on a full `tour_file` output (§11 step 3).
4.  **Type-number reuse** (64, 71, 75) between hyper-tile and Edge layouts. Branching on `is_edge_archive` is mandatory.
5.  **Phone memory and binary size.** Full Stylo + Blitz + UA fonts is heavier than the current Kotlin map. The DD-06 trigger cannot fire until Q-06 is answered.
6.  **No PDF input renderer** in the Kitesurf tree (Krilla is output). Pass 1 can look incomplete for PDF-only papers (DD-14).
7.  **Kitesurf is experimental** (README; last grounded commit 2026-11-16, `235111c`). Upstream will move. The pin is explicit (DD-17).
8.  **Host auth.** There is no CDP port in v1 (DD-41). AT-06, AT-50, AT-51, AT-87, and AT-115 remain gates. Token-file custody is the human-control point, including for the native window (DD-32, DD-60).
9.  **License completeness.** Forgetting NOTICE, MPL source, the third-party inventory, or OFL/IJG texts is a release blocker (AT-02, AT-70). The `s3a-kite` name overlaps "Kitesurf" (DD-54, Q-11).
10. **Working-archive durability and the inclusion index.** Unsealing or locking incorrectly could damage records. If `--data-dir/inclusion-index.jsonl` is lost, a later select may write a duplicate tile-10 record (DD-61 chooses that over silently dropping a real inclusion). AT-46, AT-47, AT-73, and AT-89 are gates.
